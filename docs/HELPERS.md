# Хелперы песочницы

Хелперы — это функции, доступные AI-агенту внутри сессии `rlm_execute`. Они составляют публичный интерфейс песочницы: агент пишет Python-код, вызывающий хелперы, и получает структурированные результаты. Хелперы инкапсулируют навигацию по файлам, парсинг BSL, анализ метаданных — всё, что нужно для исследования кодовой базы 1С. Агент не работает с файлами напрямую — он работает через хелперы, которые возвращают компактные словари вместо сырых данных.

## Существенные контракты

- `find_register_movements(document_name, posting_calls_offset=0)` объединяет строки main-индекса с прямыми `Движения.X` из точных ObjectModule соседних CFE. При `&Вместо("ОбработкаПроведения")`/`&ИзменениеИКонтроль(...)` main-handler движения остаются активными только когда каждая точная процедура замены напрямую вызывает `ПродолжитьВызов(...)`/`ProceedWithCall(...)`; иначе handler-only строки вынесены в `suppressed_main_code_registers`, а причина — в `_meta.cfe_posting_replacement`. Ссылки из других процедур main-модуля и движения самой CFE остаются в `code_registers`. `modules_scanned` содержит только успешно прочитанные CFE-кандидаты. При недоступном модуле helper возвращает `partial=True` и `_meta.extension_modules_unreadable`, а секция профиля — `status='unavailable'` и `_meta.partial=True`; известные положительные факты остаются в выдаче как нижняя граница. Длинные списки record set и overflow-вызовов posting-hint выдаются общей ограниченной compact-страницей, а точный вызов продолжения передаётся через `posting_calls_offset`.
- Подробный `find_register_movements` строит live-сигнал `posting_handler_present` по точным main ObjectModule из текущего CF/EDT-дерева и точным CFE ObjectModule из настроенных расширений. Поэтому main-модуль, существующий к началу сессии, участвует в сигнале независимо от свежести SQLite; индексный prefilter compact-профиля остаётся отдельным дешёвым контрактом.
- `find_based_on_documents` при существующем точном документе читает только его модули без fuzzy-cap; поиск по подстроке используется как fragment-fallback, только если точного объекта нет. Metadata-строки содержат canonical `d['ref']` (`Catalog.X`/`Document.X`); это поле используется для показа и передачи ссылки другим хелперам.
- `git_search(path=..., exclude_path=...)` нормализует внутренние Windows-разделители (`CommonModules\Foo`) и отклоняет ведущий `/` или `\`: `/CommonModules` и `\CommonModules` являются rooted-путями, а не относительным поддеревом конфигурации.
- **`limit`/`offset`: два семейства, не путать их (v1.30.0).** Слово `limit` в API означает разное:
  - **пагинация и кэп** — у подавляющего большинства хелперов. `limit` это размер страницы либо верхний предел выдачи, а `None` НЕ означает «без ограничения»: такое значение уезжает в `LIMIT ? OFFSET ?` SQLite, который требует целое. Начиная с v1.30.0 хелпер на некорректном значении не падает и не сканирует всё подряд, а **восстанавливает документированный дефолт**. Это касается `None`, строк, списков, `NaN`, а также **отрицательных чисел**: в SQLite `LIMIT -1` означает «без ограничения», и через него можно было вытянуть десятки тысяч строк в песочницу вплоть до таймаута. `0` остаётся валидным значением (пустая выдача), дробное усекается до целого.
  - **осознанное «без ограничения»** — ровно три параметра, где `None` документирован и работает как задумано: `find_event_subscriptions(limit=None)`, `find_functional_options(limit=None)` и внутренний `safe_grep(_result_cap=None)`. Их поведение не изменилось.

  Сообщение о подмене доступно **асимметрично**, и это осознанный компромисс: там, где ответ и так содержит `_meta` (`find_callers_context`, `find_definition`, `get_object_profile`, `find_code_usages`), предупреждение кладётся в `_meta.arg_warning`. Остальные возвращают список либо dict с замороженным набором ключей (например четырёхключевой ответ `count_only` у `search_regions`/`search_module_headers`) — дописывать ключи в опубликованный контракт ради диагностики нельзя, поэтому у них подмена **в ответе не сигнализируется**: понять её можно только по тому, что размер выдачи равен документированному дефолту. Внутреннее предупреждение пишется через `logger`, но в дефолтном process-режиме песочницы оно до серверного лога не доходит (у воркер-процесса нет своих обработчиков логирования) — довести его до пользователя запланировано отдельно.

## Навигация и подсказки

- `help(task)` — маршрутизатор рецептов. Вызов `help()` показывает все доступные рецепты, `help('find exports')` или `help('граф вызовов')` — конкретный рецепт с готовым Python-кодом для копирования в `rlm_execute`. Помогает слабым моделям быстро найти нужный паттерн работы

## Стандартные (из rlm-tools)

- `read_file(path)`, `read_files(paths)` — чтение файлов (кэшируется между вызовами; в MCP-сессии: с номерами строк `42 | код`)
- `grep(pattern, path)`, `grep_summary(pattern)`, `grep_read(pattern, path, max_files, context_lines)` — поиск по содержимому (grep_read совмещает поиск и чтение с контекстом в одном вызове)
- `glob_files(pattern)` — поиск файлов по маске. **При наличии SQLite-индекса** — мгновенный ответ из таблицы `file_paths` для поддерживаемых паттернов (`**/*.ext`, `Dir/**/*.ext`, `Dir/**`, `Dir/*/File.ext`, `**/Dir/**/*.ext`, `**/Name.ext`, точные пути). Остальные паттерны → fallback на `pathlib.Path.glob()`
- `tree(path, max_depth)` — дерево каталогов. **При наличии SQLite-индекса** — мгновенное построение из `file_paths` (без обхода FS)
- `find_files(name, limit)` — поиск файлов по подстроке имени. **При наличии SQLite-индекса** — мгновенный ответ с ранжированием: точное совпадение имени > префикс > подстрока имени > подстрока пути. **v1.26.0:** при нуле попаданий в индексе (zero-hit) — FS-fallback (может сканировать на большой базе), так файл из stale-индекса всё же находится; partial-hit staleness (индекс отдал старые строки) — вне scope

## BSL-специфичные (добавлены в rlm-tools-bsl)

- `find_module(name)` — найти модули объекта по имени (например, `find_module("Номенклатура")` вернёт пути к ObjectModule, ManagerModule, FormModule)
- `find_by_type(category)` — все объекты категории. Принимает как каноничные имена папок (`"InformationRegisters"`, `"Documents"`), так и сокращённые/единственное число (`"InformationRegister"`, `"Document"`) и русские (`"РегистрСведений"`, `"Документ"`, `"Справочник"`)
- `extract_procedures(path)` — извлечь сигнатуры всех Процедур/Функций из BSL-файла. **v1.23.0:** принимает rel-путь ИЛИ имя объекта (имя → авто-выбор модуля по паре `(category, module_type)`; при неоднозначности → `ValueError`, а не `[]` — для прозрачного разрешения по имени с `_meta` используй `get_module_outline`)
- `get_module_outline(path, include_methods=True, no_live=False)` — **дешёвый структурный «скелет» модуля (v1.20.0):** дерево `#Область` (с вложенностью) + агрегаты (`{methods, exports, regions, loc}`) как первый хоп перед чтением тел. Где `extract_procedures` даёт плоский список, этот хелпер показывает иерархию областей (какая процедура в какой `#Область`) и счётчики, чтобы решить, куда нырять, не читая 5–15К строк. Вложенность восстанавливается на лету из интервалов `[line, end_line]` областей/методов (в индексе родитель не хранится) — **без бампа BUILDER_VERSION**. `include_methods=False` → только дерево областей + агрегаты (ещё дешевле). Методы вне любой области → `orphan_methods`. **При наличии индекса** — один залоченный ридер (`modules`+`regions`+`methods` c `loc`); незакрытая `#Область` (`end_line=NULL`) трактуется как «до конца файла» для вложенности, в ответе `end_line` остаётся `None`. Маршрутизация на live (`extract_procedures`+`_parse_regions`) с `_meta.fallback_reason`: `index_unavailable_or_table_missing` (нет/старый индекс без таблицы `regions`, или модуль не в индексе), `index_empty_for_module` (модуль есть, методы пусты — stale, подстраховались live), `parse_failed: …`. Возвращает `{path, category, object_name, module_type, totals, outline:[{region, line, end_line, totals, children, methods}], orphan_methods, _meta:{index_used, fallback_reason, skipped_live}}`. **`no_live=False` (v1.23.0):** при `True` на stale/no-index модуле НЕ читает файл — отдаёт skipped-маркер `_meta.skipped_live=True` вместо live-fallback (так зовёт compact `get_object_profile`, чтобы секция модулей не уходила в live). **v1.23.0:** принимает rel-путь ИЛИ имя объекта (имя → прозрачный авто-выбор модуля по правилу `(category, module_type)`; resolver-ключи `resolved_from_name`/`chosen_module`/`chosen_reason`/`candidates`/`ambiguous` **домержены** в `_meta`, не затирая `index_used`/`fallback_reason`; при тай-брейке `ambiguous=True`, выбор всё равно детерминирован)
- `find_exports(path)` — только экспортные процедуры
- `read_procedure(path, name)` — прочитать тело конкретной процедуры (абсолютные номера строк). **v1.23.0 list-перегрузка:** `name` — `str` ИЛИ `list[str]` (список имён одного модуля → `{name: тело|None|{error}}`, модуль парсится ОДИН раз; в обходе проверяй `'error' in v`)
- `find_definition(name, module_hint='', limit=50)` — **где определён метод (форвард-комплемент `find_callers_context`, v1.20.0):** прямой переход к определению процедуры/функции по имени (регистронезависимо). В отличие от `_resolve_target_key` (ровно один ключ для `find_callers`) НЕ обязан разрешать в один — одноимённые методы в десятках объектов (`ОбработкаПроведения` в каждом документе) это норма 1С, поэтому возвращает всех кандидатов (потолок `limit`); сужай `module_hint` (`rel_path` | `'Документ.X'`/`'Document.X'` | голое имя объекта), чтобы запинить один. **При наличии индекса** — index-seek по `idx_meth_name` (`= ? COLLATE NOCASE`, ~3 мс на ЕРП-конфигурациях), а не SCAN; для lowercase-кириллицы (NOCASE не сворачивает кириллицу) — дешёвый `py_lower`-fallback только на пустом результате (`_meta.slow_fallback=True`). Без индекса — live через `extract_procedures` при наличии hint (`rel_path` напрямую, иначе через `find_module`); без hint → `{error:'no index', hint}`. Возвращает `{name, definitions:[{file, line, end_line, type, is_export, params (list[str]), category, object_name, module_type}], total, truncated, _meta:{index_used, unique, hint_applied, slow_fallback}}`. `hint_applied` = «фильтр по hint применён к запросу» (детерминированно), не «hint изменил число результатов». Пустой результат → `definitions:[], total:0` (не ошибка); пустой `name` → error-dict. BUILDER_VERSION не тронут (read-only поверх `methods`+`modules`)
- `find_callers(name, hint, max_files=20)` — **compact first page** того же поиска что `find_callers_context`: тонкая обёртка с default `max_files=20`, без `_meta`/пагинации, плоский `[{file, line, text}]` (3 поля) вместо `{callers:[…], _meta}` (7 полей). Quick view; если callers > `max_files` — остаток молча отбрасывается. Под капотом — тот же fast path через индекс / тот же FS-fallback. Бери `find_callers` для быстрой проверки «где зовётся»; для полного аудита callers (с `has_more` и пагинацией) — `find_callers_context`
- `find_callers_context(proc_name, module_hint, offset, limit)` — найти вызывающих с полным контекстом: имя вызывающей процедуры, флаг экспорта, категория и имя объекта, тип модуля. Фильтрует комментарии и строковые литералы. Поддерживает пагинацию. **v1.16.0:** при работе через индекс, если цель разрешается в один модуль, callers ищутся точно по `callee_key` (одноимённые методы из других модулей отсекаются), нерезолвленные name-рёбра остаются как fallback; в `_meta` добавлены `exact_rows`/`fallback_rows`/`exact_available`. Оптимизации: (1) параллельная фильтрация всех BSL-файлов через `ThreadPoolExecutor` — сканируется вся конфигурация без ограничений, на 23K файлов ~7-15 секунд; (2) результаты фильтрации кэшируются в рамках сессии — повторные вызовы мгновенны. **v1.23.0 list-перегрузка:** `proc_name` — `str` ИЛИ `list[str]` (список → `{name: {callers,_meta}|{error}}`, общий `module_hint`/`offset`/`limit` на все имена; в обходе проверяй `'error' in data`)
- `safe_grep(pattern, name_hint, max_files)` — параллельный grep по BSL-файлам через `ThreadPoolExecutor(max_workers=8)`. Результаты детерминированно отсортированы по `(file, line)`; `file` всегда POSIX-разделитель (`/`), однородно по git/Python/extension-веткам (**v1.28.0**). Безопасен на больших конфигурациях — ограничен `max_files`. **Оговорка (v1.30.0, теперь и в `sig`/`help`):** срез `max_files` действует ВСЕГДА, `name_hint` меняет лишь ТО, ЧТО режется (без hint — первые `max_files` модулей каталога, с hint — первые `max_files` СОВПАВШИХ). Поэтому пустой результат не доказывает отсутствие паттерна в конфигурации — ни без hint, ни с широким hint (общий префикс на десятки модулей). Исчерпывающий поиск — `git_search`; без git — сузить область до конкретных модулей через `find_module`/`find_by_type` и звать `safe_grep` прицельно. **Точечный** поиск по названному модулю / ограниченному набору кандидатов (для полнотекста по всей конфигурации — `git_search`, см. ниже). Контракт неизменен: всегда `[{file, line, text}]`, без усечения и sentinel. **Если исходники под git и паттерн литеральный** (без регэксп-метасимволов) — base-файлы ищутся одним вызовом `git grep` вместо пула Python-грепов (результат идентичен — литерал == подстрока, но быстрее на больших наборах кандидатов в пределах `max_files`). Регэксп-паттерны остаются на Python `re` (git `-E` это POSIX ERE, не эквивалент Python `re`); файлы расширений — всегда Python-путь. **v1.26.0 (guard вложенности):** входной паттерн ПЕРВЫМ действием проверяется на вложенные неограниченные кванторы (`(a+)+b`, `(\w+\s*)+` и т.п.) — они дают catastrophic backtracking в C-движке `_sre`, который таймаут песочницы не прерывает; при срабатывании — `ValueError` с подсказкой (литерал/`name_hint`). Это отсечение ЯВНЫХ exponential-паттернов, НЕ полноценный wall-clock-kill (нужна процессная изоляция); литералы guard'ом не затрагиваются
- `git_search(pattern, path='', file_types='', regex=False, ignore_case=False, mode='lines', max_results=200, exclude_path='')` — **полнотекстовый поиск по ВСЕМ файлам конфигурации через движок `git grep`** (доступен только когда исходники — git-рабочее-дерево). В отличие от `safe_grep` (точечно, по известному модулю) ищет в каждом отслеживаемом + новом untracked файле, **включая сырой `.xml`/`.mdo`** (формы, права ролей, СКД, ConfigDumpInfo) и тела процедур / строковые литералы / тексты запросов, которых не видят name-based хелперы и SQLite-индекс. Ищет **текущее состояние на диске** (включая незакоммиченные правки и новые untracked-файлы); `.gitignore`'d файлы не ищутся намеренно. `pattern` — подстрока (по умолчанию) либо POSIX ERE при `regex=True`. `path` — **литеральное** поддерево/файл (`"CommonModules"`; glob-метасимволы `* ? [ ]` отклоняются → error-dict, чтобы фильтр не расширялся молча; **v1.28.0**: Windows-разделитель `\` нормализуется в `/` — `path='CommonModules\Foo'` эквивалентно `'CommonModules/Foo'`, а не отбрасывается; абсолютные пути по-прежнему отклоняются → error-dict: диск (`C:\...`) и UNC/сетевой (`\\server\share\...`) — фильтр остаётся относительным поддеревом), `file_types` — список расширений (`"bsl,xml"`), композиция: `{path}/*.{ext}` (без OR-утечки между типами). `exclude_path` (**v1.20.0**) — список **литеральных** имён каталогов/файлов через запятую для отсечения шумовых зон (`'Forms,Templates'`, `'ConfigDumpInfo.xml'`); матчится на **любой глубине** (вложенный `*/Forms/*` исключается так же, как top-level — внутренне через `:(glob,exclude)**/{имя}/**`), glob-метасимволы во входе отклоняются (литерал, как у `path`); применяется поверх положительной области, без неё — по всему дереву; невалидный элемент → `[{"error": ...}]` (поиск не расширяется молча). `mode='files'` → `[{file}]` (дешёвый обзор «в каких файлах» — полезно сперва на частом токене, затем drill-down). **Гранулярность — строка, не вхождение** (как `grep`/`ripgrep`): на строку-совпадение возвращается одна запись (с полным текстом строки), даже если паттерн встречается в строке несколько раз; число записей = число совпавших строк, а не число вхождений (на файл влияет и `max_per_file`). При превышении `max_results` последний элемент — `{"_truncated": True, "shown": N}`. На сбое → `[{"error": ..., "hint": ...}]` (а не `[]`), и **форма ошибки единая — `hint` есть на КАЖДОМ ошибочном пути**. **Причина названа, а не свалена в кучу:** аргументные ошибки (`mode`, `pattern` с NL/NUL, `path`, `file_types`, `exclude_path`) классифицируются в хелпере и указывают **виновный аргумент**. Битое выражение при `regex=True` объясняет **сам git** (Python `re` — надмножество POSIX ERE: `(?=a)`, `(?P<x>a)`, `\d` компилируются здесь, но `git grep -E` их отвергает, поэтому предварительный `re.compile` — лишь быстрая отсечка, а не источник истины). **Виновника при `rc≥2` определяет stderr, а не флаг `regex`:** тем же `rc=128` git отвечает и на битое выражение, и на настоящий отказ (не git-репозиторий, повреждён индекс); ошибку компиляции git печатает **эхом паттерна** (`fatal: -e option, '(': Unmatched (`) — только тогда ответ винит `pattern`, иначе это `"git grep failed or timed out"`, и это сообщение означает **ровно** отказ git (недоступен / не репозиторий / повреждён / таймаут) при любом `regex`. **Fallback в `hint` неравноценен дважды:** `safe_grep` ищет только по BSL и без `name_hint` ограничен `max_files` кандидатами (для не-BSL и широкого поиска — `find_module`/`glob_files` + `grep` по конкретному пути), И **меняет семантику паттерна** — `git_search` по умолчанию литеральный (`git grep -F`), а `safe_grep`/`grep` компилируют аргумент как Python-regex, поэтому литеральный `(` у них упадёт ошибкой, а `.` станет «любым символом». Для литерала экранируй обе замены; исполнимый пример без скрытых переменных: `import re; p = re.escape('('); safe_grep(p, 'ИмяМодуля'); grep(p, 'конкретный/путь')` (`'('` — пример исходного литерала, путь возьми из `find_module`/`glob_files`; модуль `re` разрешен, но не предзагружен). При `regex=True` не экранируй, но помни о разных диалектах (POSIX ERE против Python `re`). **CRLF-кейвиэт**: при `regex=True` на CRLF-файлах перед концом строки стоит байт `CR`, поэтому якорь требует `[[:space:]]*$`, а не `$` (git ищет байты; POSIX ERE у `git grep` **не** трактует `\r` как возврат каретки — это литеральная `r`; и `--ignore-cr-at-eol` для grep нет). Кодировка: ожидается UTF-8 (выгрузки EDT/CF); легаси cp1251 — known limitation. Таймаут — `RLM_GIT_SEARCH_TIMEOUT` (по умолчанию 30с)

Ответ всегда разделяет `code_registers` (словари) и `erp_mechanisms`/`manager_tables`/`adapted_registers` (списки имён). `modules_scanned` содержит только успешно прочитанные ObjectModule. Недоступный CFE-модуль делает ответ неполным: helper возвращает `partial=True` и `_meta.extension_modules_unreadable`, а известные положительные факты сохраняются. При `Posting=Deny` всегда возвращаются `is_postable=False`, `posting` и hint по альтернативным связям; найденные `code_registers` сохраняются как статические ссылки с provenance, но не являются выполняемыми движениями. Если `code_registers` пуст, но live-код содержит активную `ОбработкаПроведения` или CFE-замену, возвращаются `posting_handler_present=True` и исполнимый `hint`; этот сигнал означает только отсутствие прямых активных `Движения.X`, а не наличие или отсутствие делегированных записей. Сервер разбирает точные main/CFE ObjectModule по коду без комментариев и строк, учитывает CFE-перехваты, русские и английские record set/record manager (`СоздатьНаборЗаписей`/`CreateRecordSet`, `СоздатьМенеджерЗаписи`/`CreateRecordManager`), локальные и глобальные вызовы, параметры, локальные и модульные переменные (`Перем`/`Var`), реквизиты и одноимённые общие модули; булевы операторы и `ВызватьИсключение`/`Raise` не считаются вызовами, остальные платформенные globals фильтруются в русском и English-вариантах, но одноимённое локальное объявление имеет приоритет. `Новый <Тип>(...)`/`New <Type>(...)` считается конструктором, а не dotless-вызовом. Создание набора или менеджера считается записью только при видимом `Записать()`; неразрешённые получатели и цепочки свойств помечаются как `НЕ ОПОЗНАН`. Маршрут hint выбирается по доступным возможностям (`git_search`, индексные хелперы или точечный live-поиск). Точный live-поиск объявления использует текущий файловый BSL-каталог независимо от SQLite и возвращает до 50 кандидатов; финальный `_truncated=True` означает досрочную остановку. Длинные списки record set и overflow-вызовов выдаются общей compact-пагинацией через `posting_calls_offset`; переход из compact-профиля начинает подробный маршрут с offset 0. Main `code_registers` остаются снимком SQLite, поэтому после изменения main-кода проверяется живой файл.
- `find_register_writers(register_name)` — статические ссылки документов на указанный регистр. Ответ всегда несёт `runtime_filtered=False` и `hint`: CFE-замены и `Posting=Deny` не применяются. `find_register_movements(document)` применяет эти фильтры, но main-строки в нем остаются снимком SQLite; измененный после build main-файл проверяется живьем. При наличии SQLite-индекса ответ мгновенный; без индекса выполняется параллельный поиск по всем ObjectModule
- `analyze_document_flow(document_name)` — полный жизненный цикл документа за один вызов: метаданные + подписки + движения регистров + связанные рег. задания
- `find_based_on_documents(document_name)` — ввод на основании: какие документы можно создать из этого (`ДобавитьКомандыСозданияНаОсновании`) и на основании чего можно создать его (`ОбработкаЗаполнения`). Прямые code-derived строки сохраняют прежний shape без `via` (отсутствие поля означает `direct`); обратный code-скан помечается `via='back_scan'`. **v1.28.0**: при наличии индекса `can_create_from_here` дополняется декларативными `<BasedOn>` из `metadata_references` (в т.ч. **Catalog-основания**, невидимые FS-скану `Documents/*`) — такие записи помечены `via='metadata'` и несут `category` + canonical `ref` (дедуп по `(category, object)` не схлопывает Document.X/Catalog.X-омонимы). Вход category-aware: голое имя и `Документ./Document./document./DocumentRef.` → полный обход (FS + метаданные); регистр известного английского префикса не важен. Типизированный НЕ-документ (`Справочник.X`/`catalog.X`) → только метаданные, document-specific сканы пропускаются. Если `metadata_references` недоступна, ответ содержит `partial=True`, `_meta.reason='metadata_references_unavailable'` и hint на пересборку индекса; пустые списки в этом состоянии неполны. Если authoritative count недоступен, metadata-union читает до резервного лимита: результат короче лимита полный, а результат на границе возвращает `partial=True` и `_meta.reason='metadata_references_incomplete'`, потому что за границей может оставаться хвост
- `find_print_forms(object_name)` — печатные формы объекта из `ДобавитьКомандыПечати` в ManagerModule. Распознаёт оба паттерна регистрации: helper-style (`ДобавитьКомандуПечати(КП, "Ид", НСтр(...))`) и property-style ERP 2.x (`КомандаПечати.Идентификатор = "Ид"`), с дедупликацией
- `find_functional_options(object_name, include_code=True, limit=None)` — функциональные опции, влияющие на объект: из XML метаданных + регистронезависимые BSL-вызовы `ПолучитьФункциональнуюОпцию()` в BSL-модулях. **v1.30.0 — `xml_options` матчатся ТОЧНО, а не подстрокой:** typed-ввод (`Документ.X` / `Document.X`, регистр префикса не важен) сверяется с канонической ссылкой и включает member-ссылки (`Document.X.TabularSection.Y.Attribute.Z`), но не смешивается с `Catalog.X` и не цепляет `Document.XExtra`; bare-имя матчится по ТОЧНОМУ имени объекта в любой категории (union омонимов). Подстрочный матч давал overcount: ФО попадала в выдачу, если имя встречалось лишь как ЧУЖОЙ реквизит внутри глубокой ссылки. Пустой `object_name` — прежний полный обзор всех ФО. Правило одинаково для index- и live-ветки; при этом сохраняется tri-state контракт reader'а (`None` = таблицы нет/сбой → live XML; `[]` = таблица есть, совпадений нет → окончательный ответ). Публичное поле `object` и область code-скана считаются по-прежнему (`_strip_meta_prefix`, регистрозависимо). **`code_options` остаются подстрочными** (`safe_grep(name_hint=...)`) — точность двух корзин одного ответа РАЗНАЯ, это осознанная граница релиза. Для непустого объекта code-скан использует весь текущий файловый BSL-каталог сессии, а не список модулей из SQLite-снимка; пустой обзор `find_functional_options('')` сохраняет безопасный бюджет первых 20 модулей. **v1.28.0**: `limit` (вызывать ИМЕНОВАННО — 2-й позиционный это `include_code`) — **per-bucket cap**: `xml_options` и `code_options` режутся КАЖДЫЙ независимо до N (`limit=10` → до 10+10), в ответе появляются `total`/`returned`/`has_more`. Для непустого объекта `total` считает полный XML+code-набор. Если пустой code-обзор видит больше 20 BSL-модулей, пагинированная форма возвращает `partial=True`, `_meta.reason='code_scan_budget'`, числа проверенных/всех модулей и `total_scope='all_xml_plus_scanned_code'`; `total`/`has_more` относятся только к полному XML и проверенному code-срезу. Дефолт `None` сохраняет прежний shape без пагинации
- `find_roles(object_name)` — роли с правами на объект. При наличии SQLite-индекса — мгновенный ответ из нормализованной таблицы `role_rights`. Без индекса — парсинг Rights.xml / .rights через `parse_rights_xml`, только granted-права
- `find_enum_values(enum_name)` — значения перечисления с синонимами. При наличии SQLite-индекса — мгновенный ответ из таблицы `enum_values`. Без индекса — glob + XML-парсинг. **v1.23.0 list-перегрузка:** `enum_name` — `str` ИЛИ `list[str]` (список → `{enum_name: {...}|{error}}`, изоляция ошибок поэлементно)
- `extract_queries(path)` — извлечение встроенных запросов 1С из BSL-модуля: парсит `Запрос.Текст = "..."`, многострочные `|`-тексты и (**v1.30.0**) конструкторы `Новый Запрос("...")` / `New Query("...")` плюс присваивание `Запрос.Текст =` с литералом на СЛЕДУЮЩЕЙ строке, определяет таблицы (`ИЗ РегистрНакопления.X`, `СОЕДИНЕНИЕ Справочник.Y`) и процедуру-владельца запроса. Разбор source-aware целиком, включая построчную ветку присваивания: вхождения в комментариях и внутри текста самого запроса (`ГДЕ ТекстЗапроса = "..."`) ложных записей не дают, сбор продолжений не выходит за конец своего литерала и не утаскивает следующее присваивание, несколько конструкторов на одной физической строке находятся все, служебный `|` многострочного литерала снимается, комментарий между `=` и литералом извлечению не мешает и в текст не попадает. У КОНСТРУКТОРА и перенесённой формы извлекается только статический литерал: `Новый Запрос(Переменная)`, `Новый Запрос(НСтр(...))`, конкатенация `"A" + "B"` и накопительная дописка `Запрос.Текст = Запрос.Текст + "..."` записи не дают. Однострочное присваивание работает как раньше и в этом смысле мягче: `Запрос.Текст = "ВЫБРАТЬ ..." + ДопТекст;` извлекается вместе с хвостом строки — сохранённая обратная совместимость. У новых форм `line` — строка начала выражения, `text_preview` — сам текст запроса. Однострочное присваивание идёт прежней веткой и не изменилось, включая исторический `text_preview` с хвостом строки
- `code_metrics(path)` — метрики BSL-модуля: общее число строк, строк кода/комментариев/пустых, число процедур и экспортных, средний размер процедуры, максимальная вложенность (`Если/Для/Пока`)
- `search(query, scope='all', limit=30)` — универсальный broad-first поиск: методы, объекты (синонимы), области, заголовки модулей, реквизиты, предопределённые. Fan-out по `search_methods`, `search_objects`, `search_regions`, `search_module_headers`, `find_attributes`, `find_predefined` с per-source квотой. Scope: `"all"`, `"methods"`, `"objects"`, `"regions"`, `"headers"`, `"attributes"`, `"predefined"`. Browse mode при пустом query + конкретный scope. Graceful degradation при отсутствии таблиц. Возвращает text, source_type, object_name, path, path_kind, detail
- `search_methods(query, limit=30)` — полнотекстовый поиск методов по подстроке имени во всей конфигурации. **Порог длины:** основной FTS-индекс построен по трёхсимвольным фрагментам (`tokenize='trigram'`), поэтому запрос короче 3 символов по нему не ищется вовсе; при настроенных расширениях live-ветка фильтрует подстрокой без порога, и совпадения (если они есть) придут ТОЛЬКО из расширений — ни пустой, ни extension-only ответ не доказывает отсутствия метода в основной конфигурации. Требует SQLite-индекс (FTS5, ранжирование BM25). Возвращает имя, тип, is_export, путь к модулю, имя объекта
- `search_objects(query, limit=50)` — поиск объектов 1С по бизнес-имени (русскому синониму) или техническому имени. Требует SQLite-индекс v7+ с таблицей `object_synonyms`. Кириллический case-insensitive поиск через UDF `py_lower()`. 4-уровневое ранжирование: exact name > prefix > synonym substring > category. Возвращает object_name, category, synonym (с категорийным префиксом), file
- `search_regions(query, limit=200, count_only=False, group_by=None)` — поиск областей `#Область` по имени во всей конфигурации.
  **`group_by='name'|'category'`** — топ-N групп со счётчиками вместо строк: `{group_by, groups:[{key, count}], groups_total, groups_returned, truncated, source, scope}`. Считает SQLite по ПОЛНОМУ набору, `limit` режет уже готовые группы; scope и WHERE совпадают с `count_only`, поэтому сумма `count` по ВСЕМ группам равна `count_only['total']`. Нужен потому, что списочная ветка при пустом запросе идёт `ORDER BY name`: её `limit` даёт **алфавитный префикс**, и топ-N по такому срезу систематически неверен (на боевой конфигурации топ-10 по 5000 строкам из 57 652 не пересёкся с истинным). Неизвестное значение `group_by` даёт пустые `groups` + `_meta.arg_warning` со списком допустимых — тот же контракт, что у `kinds=` в `find_references_to_object`.
  Если списочный вызов вернул РОВНО `limit` строк, в ответе `rlm_execute` приходит `efficiency_hint` с id `list_truncated:search_regions` — единственный сигнал усечения, доступный агенту (в сам список ключ не добавить, а контракт `count_only` заморожен). Требует SQLite-индекс v8+ с таблицей `regions`. Возвращает имя области, путь к модулю, диапазон строк. `count_only=True` → само-описательный dict. **Поиск идёт подстрокой без стемминга**, поэтому `'Себестоимость'` не находит `'Себестоимости'`: ноль совпадений НЕ доказывает отсутствия — проверь другую словоформу или корень. **v1.30.0**: census идёт в ТОМ ЖЕ scope, что и обычная выдача — при настроенных расширениях и непустом запросе это `{total, total_main, total_extensions, source:"index+live"|"live", truncated, scope:"main_index+live_extensions"}`. Раньше count отвечал только индексом, и `список=2 при count=1` было штатным поведением. Без расширений либо при пустом/пробельном запросе — прежний main-only `{total, source:"index"|"unavailable", truncated, scope:"main_index"}`. `limit` на count не влияет; «пустой» запрос определяется как `not query.strip()` — тем же предикатом, что у reader'а, поэтому `"   "` не запускает полный live-проход ни в count, ни в выдаче
- `search_module_headers(query, limit=200, count_only=False)` — поиск модулей по заголовочному комментарию. Требует SQLite-индекс v8+ с таблицей `module_headers`. Возвращает путь к модулю, текст заголовка. `count_only=True` → dict; **поиск без стемминга** (ноль совпадений НЕ доказывает отсутствия — проверь словоформу/корень), CFE-aware census и предикат пустого запроса — как у `search_regions` выше (**v1.30.0**)
- `get_index_info()` — метаданные индекса: версия, конфигурация, доступные возможности (FTS, синонимы). Позволяет агенту понять, какие хелперы доступны в текущей сессии
- `find_http_services(name='')` — HTTP-сервисы (REST API) конфигурации. Извлекает имя, корневой URL, шаблоны URL с HTTP-методами и обработчиками. CF и EDT форматы. Поддерживает фильтрацию по имени (LIKE)
- `find_web_services(name='')` — веб-сервисы SOAP. Извлекает имя, namespace, операции с параметрами, типами возврата и процедурами-обработчиками. CF и EDT форматы
- `find_xdto_packages(name='')` — XDTO-пакеты (контракты данных). Метаданные (имя, namespace) для обоих форматов. Типы (objectType/valueType с properties) — только для EDT (из `Package.xdto`). Для CF типы бинарные (`Package.bin`) — `types=[]`
- `find_exchange_plan_content(name)` — состав плана обмена: какие объекты входят и с каким режимом авторегистрации (Allow/Deny). CF: `Ext/Content.xml`, EDT: inline в `.mdo`. **При наличии SQLite-индекса v12+** — мгновенный ответ из таблицы `exchange_plan_content`. Без индекса — live XML-парсинг
- `find_references_to_object(object_ref, kinds=None, limit=1000)` — **аналог конфигуратора «Найти ссылки → В свойствах»** (issue [#10](https://github.com/Dach-Coin/rlm-tools-bsl/issues/10)). Поиск всех мест использования объекта метаданных. Покрывает 18 видов ссылок: `attribute_type`, `subsystem_content`, `exchange_plan_content`, `functional_option_content`, `event_subscription_source`, `role_rights`, `defined_type_content`, `characteristic_type`, `owner`, `based_on`, `main_form`, `list_form`, `default_object_form`, `default_list_form`, `command_parameter_type`, `predefined_characteristic_type` и др. Принимает русские (`Справочник.X`) и английские (`Catalog.X`, `catalog.X`, `CATALOG.X`) префиксы, Ref/Object/Manager-формы; регистр известного английского префикса не важен, в БД хранится канонический `Catalog.X`. **При наличии SQLite-индекса v12+** — мгновенный ответ из unified reverse-index таблицы `metadata_references`. На v11 — live XML-фолбэк с `partial=True`. Возвращает `{object, references: [{used_in, path, line, kind}], total, truncated, partial, by_kind}`. Поле `line` — строка САМОЙ ссылки (тег типа `<v8:Type>` в CF / `<types>` в EDT), а не объявления её владельца. Заполняется у пяти видов: `attribute_type`, `owner`, `based_on`, `default_object_form`, `default_list_form`; у остальных `line=None` — это заявленный контракт, а не пропуск (подробности и причина — в `docs/INDEXING.md`). Реквизит табличной части получает СВОЮ строку, а не первое вхождение имени по файлу; у составного типа каждый тип получает свою
- `find_code_usages(object_ref, kind=None, limit=1000)` — **обратный поиск использований объекта метаданных В КОДЕ** (дополняет `find_references_to_object`, который покрывает только декларативные ссылки из метаданных-XML). Лёгкий источник-aware regex-слой ловит три вида обращений: `manager` (`Документы.X` / `Documents.X`), `ref_type` (тип в строковом литерале `"ДокументСсылка.X"` / `"DocumentRef.X"`), `query` (путь метаданных в запросе `Документ.X` и `Документ.X.Товары` — поле `member` = имя ТЧ; многострочные запросы поддерживаются). Префикс типа принимается в RU или EN форме, регистр префикса и имени объекта не важен (нормализация + поиск по `object_ref_key`). **При наличии SQLite-индекса v13+** — мгновенный ответ из таблицы `metadata_code_usages`; на старом индексе — ограниченный `safe_grep`-фолбэк с `partial=True` (нужен rebuild). НЕ ловит доступ через локальные переменные (`Док.Товары`) и код расширений. Возвращает `{object, usages: [{path, object_name, category, module_type, line, kind, member}], by_kind, total, truncated, partial, _meta}`. Также доступен как `find_references_to_object(obj, include_code=True)` → ключи `code_*`
- `find_defined_types(name)` — раскрытие `ОпределяемогоТипа` в список реальных типов (`Catalog.X`, `Number` и т.п.). **При наличии SQLite-индекса v12+** — мгновенный ответ из таблицы `defined_types`. Без индекса — live XML-парсинг (CF: `DefinedTypes/X.xml`, EDT: `DefinedTypes/X/X.mdo`). Возвращает `{name, types: list[str], path, partial}`

## LLM-хелперы

- `llm_query(prompt, context='')` — отправить запрос в LLM (OpenAI-совместимый API). Контекст ограничен ~3000 символов. При пустом ответе — разбить контекст на части
- `llm_query_batched(prompts, context='')` — батч-запрос нескольких промптов с общим контекстом

Конфигурация провайдера: для OpenAI-совместимого пути обязательны `RLM_LLM_BASE_URL` + `RLM_LLM_MODEL` (`RLM_LLM_API_KEY` опционален); при заданном base URL fallback к Anthropic НЕ выполняется даже при одновременно заданном `ANTHROPIC_API_KEY`. Anthropic-путь выбирается только без base URL и при `ANTHROPIC_API_KEY`. Без подходящей пары env хелперы отсутствуют в `available_functions`.

**Квота**: single-вызов резервирует 1, `llm_query_batched` — атомарно весь `len(prompts)` ДО первого обращения к провайдеру (all-or-nothing: при нехватке лимита не выполняется ни один элемент батча, счётчик не меняется). Уже зарезервированный аванс при provider-ошибке или аварийном завершении worker не возвращается. В process-режиме счётчик квоты живёт в shared-памяти и переживает hard-kill worker.

**Lazy-инициализация client (v1.29.0, process-режим)**: на `rlm_start` проверяются только env-конфигурация и наличие пакета — при успешном probe хелперы уже видны в `available_functions`, а сам client создаётся при первом вызове. Если позднее создание client падает, первый `llm_query`/`llm_query_batched` возвращает bounded ошибку инициализации **без расхода квоты** (в прежнем eager-режиме такие хелперы вообще не появлялись — намеренная документированная дивергенция).

## Форматы нумерации строк (MCP-сессии)

В MCP-сессиях (через `rlm_start`) хелперы возвращают код с номерами строк:

- `42 | код` — полный файл или тело процедуры (`read_file`, `read_files`, `read_procedure`, `grep_read` с `context_lines=0`)
- `L42: код` — excerpt/контекст вокруг совпадения (`grep_read` с `context_lines>0`)

Raw API фабрик `make_helpers()`/`make_bsl_helpers()` не затронут — нумерация добавляется только в presentation layer (Sandbox).

## Таймаут и состояние сессии (v1.29.0)

- Переменные и кэши в норме сохраняются между `rlm_execute` одной сессии.
- В process-режиме (`RLM_SANDBOX_MODE=process`) таймаут — **hard-kill worker-процесса** сервером: после него всё состояние сессии (переменные, кэши, счётчики дублей) теряется, но частичный `stdout`, накопленный до kill, возвращается с маркером `... [execution terminated after timeout; partial output]`. Лимиты execute/LLM-вызовов сессии сохраняются.
- Следующий `rlm_execute` автоматически поднимает чистое поколение песочницы; его первый ответ (успешный или с обычной ошибкой кода) обязательно несёт `sandbox_state={status:"restarted", state_lost:true, generation:N}` — дальше маркер не повторяется. Ответ самого аварийного вызова несёт `sandbox_state={status:"terminated", reason:"timeout"|..., state_lost:true, restart:"on_next_execute"}`.
- В inline-режиме hard-kill не гарантируется (fallback-таймаут прежней механики) — см. [ARCHITECTURE.md](ARCHITECTURE.md).

## Расширения (CFE)

### Обнаружение и перехваты

- `detect_extensions()` — обнаружить расширения рядом с анализируемой конфигурацией (имена, пути, префиксы, назначения). Детектирование по XML-маркерам (Configuration.xml / Configuration.mdo), без хардкода имён каталогов. Каждый элемент `nearby_extensions` несёт `overrides_count` — index-side счёт перехватов по корню расширения: в MAIN-сессии `0` (нет перехватов) либо `int`, `None` если индекс расширение не покрывал (нет индекса/таблицы или EXTENSION-сессия → siblings). По СНИМКУ индекса (на stale-индексе новое расширение без строк тоже даст `0`)
- `find_ext_overrides(extension_path, object_name='')` — найти перехваченные методы в расширении: аннотации `&Перед`, `&После`, `&Вместо`, `&ИзменениеИКонтроль`. Прицельный поиск по имени объекта или полный скан всех модулей расширения. Возвращает `{extension_path, object_filter, overrides:[…] (первые 200), total, truncated, partial, _meta?}`. **v1.30.0:** строки перехватов имеют ЕДИНЫЙ набор ключей с `get_overrides` — `object_name, target_method, annotation, extension_name, extension_method, extension_root, ext_module_path, ext_line, module_path, module_type, line, source_path, source_module_id, target_method_line`; алиасы (`module_path`↔`ext_module_path`, `line`↔`ext_line`) достроены в обе стороны, недостающая привязка — `""`/`None`, но ключ есть всегда. Живые строки дополнительно получают provenance расширения — `extension_name` (имя из метаданных расширения, как у `get_overrides`) и `extension_root` (переданный путь), поэтому выдачу по нескольким расширениям можно объединять и группировать по имени. Изменения только аддитивные: значения существующих полей и ПОРЯДОК среза 200 (порядок обхода файлов) не изменились. `extension_method` по-прежнему может быть пустым у перехвата, объявление которого отделено от аннотации длинным блоком комментариев — read-time лечение таких строк остаётся известным ограничением. `partial=True` означает, что часть BSL-файлов или дерева каталогов не прочитана; детали находятся в `_meta.scan_diagnostics`, а `total` является нижней оценкой.
- `get_overrides(object_name='', method_name='')` — запрос перехватов из индекса (v9+) с live fallback на старом индексе или без него. Возвращает `{overrides: [...] (первые 200, детерминированно отсортированы), total, truncated, partial, source: "index"|"live"|"unavailable", by_annotation, by_object_top, by_extension_top, unique_objects, unique_methods, unique_extensions, _meta?}`. При `partial=False` агрегаты считаются по полному выбранному источнику: `by_annotation` содержит все аннотации, `by_object_top`/`by_extension_top` — top-20, `unique_*` — полные количества. При `partial=True` live-скан прочитан не полностью: `total` и агрегаты являются нижней оценкой, а недочитанные корни перечислены в `_meta.failed_extension_roots`; если ни один корень не удалось просканировать, `source="unavailable"`. Срез `overrides` не используется для самостоятельного подсчёта агрегатов; при `truncated=True` для детализации применяется фильтр по объекту/методу или `find_ext_overrides` по конкретному расширению. Группировка регистронезависима, shape одинаков для веток `index`/`live`/`unavailable`. `by_annotation`/`by_object_top`/`by_extension_top` — это **dict `{имя: количество}`** (топ-20 у двух последних), а не список записей: итерировать через `.items()`. `target_method_line=None` — ВАЛИДНОЕ значение (перехват предопределённого события платформы без текстового объявления в базовом модуле либо строка без source-привязки), не ошибка индекса. **v1.30.0:** строки несут единый набор ключей с `find_ext_overrides` (см. выше), при неизменном составе и порядке среза 200 — он фиксируется ключом сортировки, вычисленным ДО обогащения.
- `extract_procedures(path)` — при наличии индекса v9+ каждый перехваченный метод содержит поле `overridden_by` со списком перехватов (аннотация, расширение, метод, путь, строка)
- `read_procedure(path, proc_name, include_overrides=False)` — с `include_overrides=True` дописывает тело расширенного метода с аннотацией и файловой ссылкой (override-тела тоже нумеруются в MCP-сессии). Без параметра — обратная совместимость, чистое тело

### Видимость объектов и модулей расширений из main-сессии (v1.12.0)

При открытии сессии на основной конфигурации с соседними CFE-расширениями (`src/cf/` + `src/cfe/<name>/`) высокоуровневые BSL-хелперы видят и объекты, и модули расширений — без переоткрытия сессии в каталоге самого расширения. Пути таких объектов возвращаются с префиксом `../cfe/...` относительно sandbox base.

- `find_module(name)` / `find_by_type(category, name='')` — возвращают модули из соседних расширений вместе с main-модулями
- `find_attributes(name=...)` (без `object_name`) / `find_predefined(name=...)` (без `object_name`) — name-only поиск дополняется live-сканом ext-объектов; результаты ext-стороны участвуют в общем 3-уровневом ранкинге (exact > prefix > substring) по `attr_name`/`attr_synonym` (для предопределённых — `item_name`/`item_synonym`). Поле `source_file` в каждой row содержит путь к XML расширения, чтобы `search(query, scope='attributes'|'predefined')` отдавал непустой `path`
- `find_attributes(object_name="Catalogs/ExtOnly")` / `find_predefined(object_name=...)` / `parse_object_xml("Catalogs/ExtOnly")` — резолвят XML-only объекты расширений (Subsystems, EventSubscriptions без `<Synonym>`)
- `search_methods(query)` / `search_objects(query)` / `search_regions(query)` / `search_module_headers(query)` — индексные результаты дополняются live-данными из расширений; shape (`rank=None` для методов, prefixed `Категория: Синоним` для объектов) точно зеркалит `IndexReader`. Merge выполняется **до** truncation: ext-объект с exact-name match занимает слот в топе, даже когда main-индекс уже вернул `limit` rank-2 совпадений
- `search_objects("")` (alphabetical listing) — ext-синонимы тоже включаются в общую alphabetical-сортировку, не отбрасываются на saturated main
- `read_procedure(ext_path, name)` / `extract_procedures(ext_path)` — принимают пути с префиксом `../cfe/...` напрямую и читают содержимое расширения через `_ext_read_file` (multi-root резолвер с собственным кэшем чтения)

**Sandbox-инвариант сохраняется:** пользовательский `read_file('../cfe/...')`, `grep`, `glob_files` на `../`-пути по-прежнему возвращают `PermissionError`. Видимость расширений добавлена только в высокоуровневые BSL-хелперы. Если `find_module` вернул путь с `../` — передавай его именно в `read_procedure`/`extract_procedures`/`parse_object_xml`/`find_attributes`/`find_predefined`/`search`, а не в generic I/O.

### Multi-line сигнатуры и opportunistic live-fill (v1.12.0)

- Многострочные `Процедура X(a,\n  b,\n  c)` и `Функция` корректно парсятся индексером и live-хелпером через общий util `bsl_knowledge._merge_proc_continuations` — склейка продолжений с учётом строковых литералов и hard-cap (20 строк / 2000 символов на сигнатуру)
- `extract_procedures(path)` для индексированных путей делает **opportunistic live-fill**: если индекс пропустил multi-line процедуру (старый builder), live-парсер дополняет результат с тем же shape, включая enrichment `overridden_by` из индекса. Поведение self-healing — multi-line процедуры видны сразу после обновления пакета, без обязательного `rlm-bsl-index index update`

## Оптимизации для совместимости с разными AI-моделями

При тестировании с различными AI-клиентами и моделями (Kilo Code + minimax m2.5, glm-5, Nvidia Nemotron, gpt-5.4; Claude Code + Sonnet 4.6) были выявлены проблемы: слабые модели не понимали парадигму песочницы, путали хелперы с MCP-инструментами, не знали форматы возвращаемых данных. Для решения этих проблем внесены следующие оптимизации:

- **Пошаговый WORKFLOW** — ответ `rlm_start` содержит пошаговый план работы (DISCOVER → READ → TRACE → ANALYZE → EXTENSIONS) с указанием конкретных хелперов на каждом шаге. Компактная таблица хелперов с возвратными типами. Детальные рецепты с Python-сниппетами доступны через `help('keyword')` внутри песочницы
- **Хелпер `help(task)`** — интерактивный маршрутизатор рецептов внутри песочницы (см. выше)
- **Толерантный `find_by_type`** — принимает категории в единственном числе (`"Document"` вместо `"Documents"`), русские названия (`"Справочник"`, `"РегистрСведений"`), регистронезависимо
- **Параллельный prefilter в `find_callers_context`** — `ThreadPoolExecutor` сканирует **все** BSL-файлы конфигурации параллельно (~7-15 секунд на 23K файлов), без лимита и усечения. Результаты кэшируются в рамках сессии — повторные вызовы мгновенны
- **Grep guard** — защита от широких путей. Вызов `grep(pattern, '.')` или `grep(pattern, 'CommonModules')` на конфигурации с >5000 файлов мгновенно возвращает ошибку с подсказкой вместо 60-секундного таймаута. `grep` на конкретных файлах и небольших каталогах работает как обычно
- **Делегирование `find_callers` → `find_callers_context`** — `find_callers()` это compact first page над `find_callers_context()`. Под капотом — тот же поиск (индекс / параллельный prefilter), но контракт урезан до `[{file, line, text}]` без `_meta`/пагинации, default `max_files=20`. Слабая модель получит работоспособный quick view; для полного аудита (`has_more`, пагинация) — прямой вызов `find_callers_context()`
- **Авто-детект нетиповых префиксов** — при старте сессии анализируются имена объектов в индексе, выделяются частотные lowercase-префиксы. Порог: 3+ вхождения для основных конфигураций, 1 для расширений (определяется по `config_role` из индекса). При наличии SQLite-индекса префиксы читаются из `index_meta` (мгновенно), без индекса — сканирование объектов. Результат возвращается в `detected_custom_prefixes` ответа `rlm_start` и в блоке DETECTED CUSTOM PREFIXES стратегии
- **Auto-strip типа метаданных** — все хелперы автоматически очищают префикс типа (`Документ.РеализацияТоваровУслуг` → `РеализацияТоваровУслуг`). Модель может передавать имена в любом формате без ошибок
- **Авто-детект расширений** — при старте сессии определяется роль конфигурации (основная/расширение) по XML-маркерам (Configuration.xml / Configuration.mdo). Автоматически сканируются соседние каталоги (1-2 уровня вверх) на наличие расширений или основной конфигурации. Результат — в `extension_context` ответа `rlm_start` и top-level `warnings`. В стратегии — CRITICAL-блок с директивами `YOU MUST` для проверки перехватов. Поддерживаются аннотации `&Перед`, `&После`, `&Вместо`, `&ИзменениеИКонтроль`
- **Структурированная стратегия** — ответ `rlm_start` содержит пошаговый WORKFLOW (DISCOVER → READ → TRACE → ANALYZE → EXTENSIONS) вместо монолитного текста. Секции с заголовками `== SECTION ==`, компактная таблица хелперов с возвратными типами, ссылки на `help('keyword')` для детальных рецептов
- **SQLite Level-3 ускорение** — при наличии индекса `find_roles()`, `find_register_movements()`, `find_register_writers()` работают мгновенно из нормализованных таблиц `role_rights` и `register_movements`. Таблица `role_rights` строится параллельно с BSL regex-парсингом (CF: Rights.xml, EDT: .rights). Таблица `register_movements` извлекается in-band при обработке BSL-файлов документов (без дополнительного I/O). Без индекса — fallback на live-парсинг XML и grep
- **Описания MCP-инструментов** — docstrings `rlm_start` и `rlm_execute` явно указывают, что `code` — это Python-код, что нужно использовать `print()`, содержат пример вызова

## Индекс и слабые модели

Без предварительно построенного индекса (`rlm-bsl-index index build <path>`) слабые модели (Kilo Auto, Qwen 3.6 Plus, Minimax и др.) не смогут качественно выполнить анализ:

- `find_attributes(name=...)`, `find_predefined(name=...)`, `search()`, `search_methods()`, `search_objects()`, `search_regions()`, `search_module_headers()` — возвращают пустые результаты без индекса
- `find_attributes(object_name=...)`, `find_predefined(object_name=...)` — работают через XML-fallback, но требуют многошаговой логики (find_module → category → XML-парсинг)

Сильные модели (Claude Sonnet/Opus, GPT) способны самостоятельно выстроить цепочку fallback-вызовов. Слабые модели видят пустой результат и сдаются, не пытаясь использовать альтернативные хелперы.

**Рекомендация:** всегда стройте индекс перед работой со слабыми моделями. Для сильных моделей индекс опционален, но значительно ускоряет анализ (1s vs 20-50s на старт сессии, мгновенные поиски vs таймауты на find_roles/find_functional_options).
