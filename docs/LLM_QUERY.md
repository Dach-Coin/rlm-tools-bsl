# Настройка и механика llm_query

## Что это и зачем

В песочнице rlm-tools-bsl есть хелперы `llm_query(prompt, context)` и `llm_query_batched(prompts, context)` — они вызывают «маленькую» LLM прямо из `rlm_execute`, не возвращаясь в основной контекст агента. Это **вспомогательная** LLM, которая работает на стороне сервера.

### Когда это окупается

Правило одно: **`llm_query` окупается ровно тогда, когда сжатие требует суждения.** Если сокращение выражается кодом — LLM не нужна, код точнее, быстрее и не тратит квоту:

```python
# так — не нужна LLM: критерий детерминированный
# префиксы доработок сервер отдаёт сам, в rlm_start.detected_custom_prefixes
custom = [n for n in names if n.lower().startswith(tuple(prefixes))]
```

Суждение требуется там, где критерий нельзя записать условием:

- **Ранжирование по намерению** — «из 100 совпадений `git_search` оставь 5, относящихся к расчёту скидки». Никакое регулярное выражение не выражает «относящихся к».
- **Классификация по нечёткой бизнес-категории** — «какие из этих методов относятся к проведению, а не к заполнению». По именам не решается: `ДанныеДокументаДляПроведения` и `ЗаполнитьДокументНаОсновании` различаются смыслом, а не подстрокой.
- **Сжатие тела в намерение** — «что делает эта процедура на 300 строк, одним предложением». В контекст агента вместо 3–4 тысяч токенов приходит одна фраза.
- **Извлечение из прозы** — заголовки модулей, комментарии, тексты запросов: «какие из этих 50 заголовков говорят про интеграцию с банком».

Выигрыш **растёт с разветвлением**. На конфигурации в сотни тысяч методов широкий вопрос даёт списки в сотни позиций — там сжатие доходит до 100:1. На списке из 15 позиций смысла нет: агент прочитает его сам дешевле, чем стоит вызов.

Отдельно — `llm_query_batched`: **N независимых суждений по одному и тому же контексту**, посчитанных параллельно (до 8 потоков). Экономит он **только время**. Ни токенов, ни контекста агента батч не сберегает:

- контекст подставляется в каждый из N запросов и уходит провайдеру N раз — батч из 5 промптов по контексту в 10 КБ это 50 КБ входа, а не 10;
- контекст агента экономит сам `llm_query`, а не батч: те же N вызовов подряд **внутри одного** `rlm_execute` вернут агенту ровно столько же;
- квота расходуется одинаково — `len(prompts)` единиц в обоих случаях.

Отсюда практическое следствие: если вопросов много, а контекст большой, дешевле задать один промпт, просящий всё сразу, чем N по отдельности. Батч оправдан, когда контекст мал относительно числа суждений или когда важна задержка.

### Когда НЕ стоит

- **Критерий выразим кодом.** Префикс, тип модуля, наличие подстроки, категория объекта — всё это уже есть в индексе и в полях хелперов.
- **Список короткий.** До ~20 позиций дешевле вернуть как есть.
- **Нужен точный идентификатор.** Sub-LLM может выдать правдоподобное, но несуществующее имя метода, и агент пойдёт читать пустоту. Рабочий режим: **`llm_query` сужает — индекс подтверждает**. Как финальный источник имён для навигации sub-LLM использовать нельзя.
- **Ответ должен быть воспроизводимым.** Один и тот же запрос к одной и той же модели даёт разные ответы; для гейтов и проверок это негодный инструмент.

### Пример: классификация по смыслу

```python
# Агент выполняет в rlm_execute:
procs = extract_procedures("Documents/ИмяДокумента/Ext/ObjectModule.bsl")
names = sorted({p["name"] for p in procs})

result = llm_query(
    "Из списка имён методов выбери максимум 10, относящихся к ПРОВЕДЕНИЮ "
    "(движения, регистры, отражение в учёте). Только имена через запятую.",
    context=", ".join(names),
)
print(result)
```

Критерий «относится к проведению» не выражается фильтром — это и есть случай для sub-LLM. Полученные имена дальше **проверяются по индексу** (`find_definition`, `read_procedure`), а не принимаются на веру.

### Проверка тоже должна быть правильной

Сверять ответ обязательно — но наивная сверка «встречается ли строка дословно» даёт ложные обвинения. 1С ссылается на метаданные минимум тремя способами, и совпадать с формой ответа модели они не обязаны:

| Как в коде | Как назовёт модель |
|---|---|
| `ПолучитьФункциональнуюОпцию("ИспользоватьСоглашения")` | `ФункциональныеОпции.ИспользоватьСоглашения` |
| реквизит типа `СправочникСсылка.Склады` | `Справочник.Склады` |
| `Перечисления.СтатусыЗаказов.Закрыт` | `Перечисления.СтатусыЗаказов` |

На реальной проверке пересказа процедуры это дало 7 «галлюцинаций» из 14 — и все семь оказались **корректными** ответами, приведёнными к канонической форме. Дословный поиск подстроки осудил бы правильный результат и отправил бы разработчика искать несуществующую проблему.

Практическое правило: сверяйте по **имени объекта**, а не по полной квалифицированной строке, и считайте расхождение формы нормой, а не ошибкой. Настоящая галлюцинация — это когда объекта с таким именем в конфигурации нет вообще; вот это и проверяется индексом (`search_objects`, `find_attributes`, `find_definition`).

### Чего ожидать от качества

Sub-LLM — вспомогательный инструмент, а не источник истины. Что важно знать заранее:

- **Неверное сжатие незаметно.** Агент видит только ответ и не знает, что было отброшено. Поэтому sub-LLM ставят на шаг **сужения**, за которым идёт детерминированная проверка, а не на шаг принятия решения.
- **Лимит токенов важнее, чем кажется.** Многие современные модели тратят часть бюджета на внутреннее рассуждение, причём ряд провайдеров отдаёт его не отдельным полем, а прямо внутрь текста ответа. Тогда потолок обрывает ответ на полуслове, и обрывок выглядит как полный ответ. На замере с контекстом 16 КБ при `max_tokens=1024` ответ был непригоден в 5 случаях из 6, при 2048 — в 2 из 6, при 4096 — ни разу. Поэтому по умолчанию стоит 2048, а на тяжёлых задачах есть смысл поднять `RLM_LLM_MAX_TOKENS` до 4096. Обрыв теперь виден: к неполному ответу дописывается хвост `[TRUNCATED]` (см. ниже).
- **Цена растёт не пропорционально потолку.** `max_tokens` — предел, а не расход: на коротких запросах он не достигается и не стоит ничего. В том же замере средний расход при переходе 1024 → 2048 вырос с 920 до 1192 токенов, потому что при 1024 модель просто упиралась в предел и тратила его впустую.
- **Квота конечна.** На `effort=high` это 30 вызовов sub-LLM на 50 `rlm_execute` — примерно каждый второй шаг. Тратить её стоит на шаги с наибольшим разветвлением.
- **Дешёвые модели годятся для рутины** — классификация, суммаризация, извлечение ключевых слов не требуют мощной модели. Но чем слабее модель, тем строже должно быть последующее подтверждение по индексу.

## Настройка LLM-провайдера

Поддерживаются два варианта подключения (достаточно одного):

### OpenAI-совместимый endpoint (OpenRouter, LiteLLM, Ollama, vLLM)

```bash
# Windows
set RLM_LLM_BASE_URL=http://localhost:11434/v1
set RLM_LLM_API_KEY=
set RLM_LLM_MODEL=qwen2.5:7b

# Linux/macOS
export RLM_LLM_BASE_URL=http://localhost:11434/v1
export RLM_LLM_API_KEY=
export RLM_LLM_MODEL=qwen2.5:7b
```

| Переменная | Обязательность | Описание |
|---|---|---|
| `RLM_LLM_BASE_URL` | обязателен | Базовый URL endpoint'а |
| `RLM_LLM_MODEL` | обязателен | Имя модели |
| `RLM_LLM_API_KEY` | опционален | API-ключ (может быть пустым, например для Ollama) |
| `RLM_LLM_MAX_TOKENS` | опционален | Максимум токенов ответа (по умолчанию 2048). Действует и на Anthropic-путь |
| `RLM_LLM_EXTRA_BODY` | опционален | JSON-объект с дополнительными полями тела запроса (`extra_body` в OpenAI SDK). **Только этот провайдер** |

Требует пакет `openai` (входит в основные зависимости, ставится автоматически).

### Anthropic API

```bash
# Windows
set ANTHROPIC_API_KEY=sk-ant-api03-...

# Linux/macOS
export ANTHROPIC_API_KEY=sk-ant-api03-...
```

| Переменная | Обязательность | Описание |
|---|---|---|
| `ANTHROPIC_API_KEY` | обязателен | Ключ с [console.anthropic.com](https://console.anthropic.com) → API Keys |
| `RLM_SUB_MODEL` | опционален | Модель (по умолчанию Claude Haiku) |
| `RLM_LLM_MAX_TOKENS` | опционален | Максимум токенов ответа (по умолчанию 2048) |

`RLM_LLM_EXTRA_BODY` на Anthropic-путь **не действует**: это расширения OpenAI-совместимого протокола, у Anthropic поля другие.

### Приоритет провайдеров

Если заданы и `RLM_LLM_BASE_URL`, и `ANTHROPIC_API_KEY` — приоритет у OpenAI-совместимого endpoint'а.

## Как передать переменные окружения

- **stdio** — через секцию `env` в конфиге MCP (см. [INSTALL.md](INSTALL.md))
- **StreamableHTTP** — через файл `.env` рядом с рабочим каталогом, откуда запускается сервер. Сервер вызывает `load_dotenv(override=True)` при старте

Пример `.env`:
```
RLM_LLM_BASE_URL=https://api.kilo.ai/api/gateway
RLM_LLM_API_KEY=your-api-key
RLM_LLM_MODEL=minimax/minimax-m2.5:free
```

## Техническая механика

### llm_query(prompt, context)

1. Проверяет квоту LLM-вызовов сессии (зависит от effort-уровня)
2. Если передан `context`, формирует промпт: `"Context:\n{context}\n\nQuestion: {prompt}"`
3. Отправляет запрос в настроенный LLM-провайдер
4. Ограничение ответа: по умолчанию **max_tokens=2048** на каждый вызов, переопределяется `RLM_LLM_MAX_TOKENS`
5. Возвращает текст ответа как строку. Если текста нет — вместо него приходит диагностический маркер; если текст есть, но оборван лимитом — к нему дописывается хвост `[TRUNCATED]` (см. ниже)

### Диагностика ответа (только OpenAI-совместимый провайдер)

> Всё, что описано в этом разделе, работает **только на OpenAI-совместимом пути**. Anthropic-провайдер маркеров не выставляет: там своя схема завершения (`stop_reason="max_tokens"`), и обрыв ответа остаётся неотмеченным. Это осознанная граница релиза, а не недосмотр.

Симптом: запрос завершается успешно (HTTP 200), но `content` пустой, а `finish_reason` — `length`. Это значит, что весь токен-бюджет ушёл на внутренние размышления модели (`reasoning_content`), и на сам ответ ничего не осталось. Раньше `llm_query` возвращал в этом случае пустую строку, и отличить «модель ничего не нашла» от «бюджет съеден» было невозможно.

Теперь вместо пустой строки возвращается короткий маркер. Он **не** содержит ни промпта, ни ответа, ни самого текста размышлений, ни API-ключа — только причину:

| Маркер | Когда | Что делать |
|---|---|---|
| `[EMPTY] … Бюджет ушёл в reasoning; …` | `finish_reason=length`, либо модель прислала непустой `reasoning_content` **и при этом не назвала явную причину** | Поднять `RLM_LLM_MAX_TOKENS` **или** отключить thinking через `RLM_LLM_EXTRA_BODY` |
| `[EMPTY] … finish_reason=content_filter …` | Явная причина от провайдера (`content_filter`, `tool_calls`, `function_call`) — **приоритетнее** признака reasoning | Лимит тут не при чём — смотреть на саму причину |
| `[REFUSAL] <текст>` | Модель ответила отказом (поле `refusal`) | Это и есть ответ модели |
| `<ответ>` + хвост `[TRUNCATED] …` | `finish_reason=length` при **непустом** ответе — модель оборвал потолок | Ответ НЕПОЛНЫЙ. Поднять `RLM_LLM_MAX_TOKENS` или сузить контекст |
| `[ERROR] …` | Провайдер вернул ответ неожидаемой формы или `content` не строкой | Проблема на стороне endpoint'а; в маркере — только имя типа, без значения |

Пустой `choices` (модель не вернула ни одного варианта) по-прежнему даёт пустую строку — сообщать там нечего.

**Как разбирать ответ с хвостом `[TRUNCATED]`.** Хвост отделён пустой строкой и приписан в конец, поэтому тело ответа остаётся неизменным — но наивный разбор всё-таки заденет: у `ответ.split(", ")` маркер попадёт в ПОСЛЕДНИЙ элемент. Сначала отделяйте хвост, потом разбирайте:

```python
answer = llm_query(...)

# Ищем ТОЧНЫЙ разделитель, а не подстроку "[TRUNCATED]": ответ может сам
# обсуждать этот маркер, и тогда проверка по вхождению отрежет живой абзац.
body, sep, note = answer.rpartition("\n\n[TRUNCATED] ")
if not sep:
    # Разделителя нет — ответ полный. ВАЖНО: rpartition без совпадения кладёт
    # всю строку в ТРЕТИЙ элемент, поэтому body здесь пустой и его надо вернуть.
    body, note = answer, None
if note:
    print("ВНИМАНИЕ: ответ неполный —", note)

items = [x.strip() for x in body.split(",")]
```

Два способа лечения reasoning-случая:

```env
# 1. Отключить thinking (Z.AI и совместимые)
RLM_LLM_EXTRA_BODY={"thinking":{"type":"disabled"}}

# 2. Или просто дать больше бюджета
RLM_LLM_MAX_TOKENS=4096
```

### llm_query_batched(prompts, context)

1. Принимает список промптов и общий контекст. Контекст **подставляется в каждый** промпт и уходит провайдеру `len(prompts)` раз — выигрыш батча только во времени, не во входных токенах и не в контексте агента
2. Параллельно отправляет запросы через `ThreadPoolExecutor(max_workers=8)`
3. Если один промпт упал с ошибкой — остальные продолжают работать, для упавшего возвращается `"[ERROR] ..."`
4. Результаты возвращаются в порядке исходных промптов

### Квоты по effort-уровням

| Effort | Макс. LLM-вызовов | Макс. rlm_execute |
|--------|-------------------|-------------------|
| low    | 5                 | 10                |
| medium | 15                | 25                |
| high   | 30                | 50                |
| max    | 50                | 100               |

`llm_query` резервирует 1 вызов, `llm_query_batched(prompts)` — `len(prompts)` вызовов. При превышении квоты — `RuntimeError`.

## Без настройки LLM

**Всё остальное работает нормально** — `find_module`, `grep`, `read_file`, `parse_object_xml` и все прочие хелперы не требуют API-ключа. Просто `llm_query()` будет недоступен.

Базовая функциональность rlm-tools-bsl не пострадает. Однако в отдельных сложных случаях основная модель-анализатор получит неранжированный ответ и потратит больше токенов на поиск сути — вместо того чтобы получить компактную выжимку от sub-LLM.
