# Справочник переменных окружения

Все переменные окружения, поддерживаемые rlm-tools-bsl. Ни одна из них не является обязательной — сервер запускается и работает с настройками по умолчанию.

Переменные можно задать:
- В файле `.env` рядом с рабочим каталогом (для StreamableHTTP — `load_dotenv(override=True)` при старте)
- В секции `env` конфига MCP (для stdio-транспорта)
- В окружении системы

Пример `.env` — см. файл `.env.example` в корне репозитория.

**Парсинг inline-комментариев в `.env`:**
- Значения в кавычках: `#` внутри сохраняется — `PASSWORD="p@ss#word"` → `p@ss#word`
- Без кавычек: inline-комментарий только через ` #` (с пробелом) — `URL=https://host#frag` → сохраняется, `KEY=value # comment` → `value`
- Экранированные кавычки внутри значений (`\"`) не поддерживаются — используйте одинарные кавычки или избегайте кавычек в значении

### Пример рабочей конфигурации

```env
# LLM через OpenAI-совместимый gateway (Kilo AI, free-модель)
RLM_LLM_BASE_URL=https://api.kilo.ai/api/gateway
RLM_LLM_API_KEY=your-kilo-api-key
RLM_LLM_MODEL=kilo-auto/free

# Индексы хранятся в отдельном каталоге (не в домашней папке)
RLM_INDEX_DIR=D:\Indexes\1C

# Проверка свежести индекса — расширенная выборка
RLM_INDEX_MAX_AGE_DAYS=7
RLM_INDEX_SAMPLE_SIZE=20
RLM_INDEX_SAMPLE_THRESHOLD=30

# Полное логирование хелперов (для отладки)
RLM_LOG_HELPERS=all
```

## LLM-провайдер для llm_query()

Хелперы `llm_query()` и `llm_query_batched()` вызывают вспомогательную LLM прямо из песочницы. Без настройки провайдера эти хелперы недоступны, всё остальное работает нормально. Подробнее — [LLM_QUERY.md](LLM_QUERY.md).

### OpenAI-совместимый endpoint (приоритетный)

| Переменная         | По умолчанию | Описание                                                                                                                                                                      |
| ------------------ | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_LLM_BASE_URL` | —            | Базовый URL endpoint'а (например `http://localhost:11434/v1` для Ollama, `https://openrouter.ai/api/v1` для OpenRouter). Если задан — активирует OpenAI-совместимый провайдер |
| `RLM_LLM_MODEL`    | —            | Имя модели (обязателен при заданном `RLM_LLM_BASE_URL`). Примеры: `qwen2.5:7b`, `minimax/minimax-m2.5:free`                                                                   |
| `RLM_LLM_API_KEY`  | `""`         | API-ключ. Может быть пустым (Ollama, vLLM без авторизации)                                                                                                                    |

### Параметры запроса sub-LLM

| Переменная             | По умолчанию | Описание                                                                                                                                                                                                                              |
| ---------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_LLM_MAX_TOKENS`   | `2048`       | Максимум токенов ответа sub-LLM. Положительное целое. Применяется к **обоим** провайдерам — и к OpenAI-совместимому, и к Anthropic                                                                                                      |
| `RLM_LLM_EXTRA_BODY`   | —            | JSON-объект с дополнительными полями тела запроса. **Только OpenAI-совместимый провайдер** (передаётся в SDK как `extra_body`); на Anthropic-путь не действует. Ключи `model`, `messages`, `max_tokens`, `stream` задаются самим запросом и отбрасываются |

Пример для reasoning-модели, которая расходует весь лимит на размышления и возвращает пустой ответ (Z.AI и совместимые):

```env
RLM_LLM_EXTRA_BODY={"thinking":{"type":"disabled"}}
```

Альтернатива без отключения thinking — просто поднять лимит:

```env
RLM_LLM_MAX_TOKENS=4096
```

> Непригодное значение любой из двух переменных **не роняет сервер и не отключает `llm_query`**: в `server.log` пишется предупреждение с именем переменной и причиной, а работа продолжается на значении по умолчанию. Подробнее про диагностику пустого ответа — [LLM_QUERY.md](LLM_QUERY.md).

### Anthropic API (резервный)

| Переменная          | По умолчанию                | Описание                                                                                                                                       |
| ------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `ANTHROPIC_API_KEY` | —                           | API-ключ с [console.anthropic.com](https://console.anthropic.com) → API Keys. Активирует Anthropic-провайдер, если `RLM_LLM_BASE_URL` не задан |
| `RLM_SUB_MODEL`     | `claude-haiku-4-5-20251001` | Модель Anthropic для sub-LLM запросов                                                                                                          |

> Если заданы и `RLM_LLM_BASE_URL`, и `ANTHROPIC_API_KEY` — приоритет у OpenAI-совместимого endpoint'а.

| --------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_MAX_SESSIONS`    | `5`          | Максимальное количество одновременных сессий                                                                                           |
| `RLM_SESSION_TIMEOUT` | —            | Единый таймаут сессии (минуты). Если задан — переопределяет оба таймаута ниже (backward compat)                                        |
| `RLM_SESSION_TIMEOUT_IDLE` | `10`    | Таймаут idle-сессии (минуты) — сессия без единого execute-вызова (calls=0)                                                              |
| `RLM_SESSION_TIMEOUT_ACTIVE` | `30`  | Таймаут активной сессии (минуты) — сессия с execute_calls>0                                                                             |
| `RLM_TRANSPORT`       | `stdio`      | Транспорт MCP-сервера: `stdio` или `streamable-http`. Можно также задать через аргумент `--transport` при запуске                      |
| `RLM_HOST`            | `127.0.0.1`  | Адрес для HTTP-транспорта. Можно также задать через `--host`                                                                           |
| `RLM_PORT`            | `9000`       | Порт для HTTP-транспорта. Можно также задать через `--port`                                                                            |
| `RLM_CONFIG_FILE`     | —            | Путь к `service.json`. Каталог этого файла определяет расположение `projects.json`, `.env`, `logs/` и `cache/`. Если не задан — `~/.config/rlm-tools-bsl/service.json` для конфига и `~/.cache/rlm-tools-bsl/` для кэша |
| `RLM_STDIO_HARDENING` | включено     | Разводка стандартных дескрипторов при `stdio`-транспорте: протокол обслуживается с приватных дубликатов fd 0/1, а сами fd 0 и 1 уводятся на `os.devnull` и на stderr, чтобы дочерние процессы (sandbox-worker, `git`) не наследовали протокольные трубы, а посторонний вывод (`print()`, raw-запись в дескриптор 1, вывод детей) не попадал в поток протокола. Последняя гарантия опирается на раздельные stdout/stderr: при запуске сервера с `2>&1` отвод и есть протокольная труба. Отключается значениями `0`, `false`, `no`, `off`; на `streamable-http` не действует вовсе. **Отключать не рекомендуется**: на Windows без разводки дочерний Python зависает внутри инициализации интерпретатора, и `rlm_start` в режиме `RLM_SANDBOX_MODE=process` падает по `RLM_SANDBOX_START_TIMEOUT_SECONDS` |

## Песочница `rlm_execute` (процессная изоляция, v1.29.0)

С v1.29.0 код агента может выполняться в отдельном sandbox-worker-процессе на каждую сессию (`RLM_SANDBOX_MODE=process`): stdout разных сессий физически разделён процессами, timeout — авторитетный hard-kill со стороны родителя (Windows Job Object / POSIX process group), падение/OOM worker не роняет MCP-сервер. Режим `inline` (код в основном процессе, как до v1.29.0) остаётся только для диагностики и аварийного ручного восстановления — он небезопасен: hard process isolation отключена, timeout не гарантирует остановку кода. Все inline-execute при этом глобально сериализованы (stdout-гонка закрыта и там ценой параллельности).

**Невалидное или пустое явно заданное значение `RLM_SANDBOX_MODE` — это ошибка старта сервера (fail-fast), а не fallback**: опечатка не имеет права незаметно отключить заявленную границу изоляции. Автоматического отката `process` → `inline` при ошибке spawn/Job Object нет: `rlm_start` возвращает controlled error.

| Переменная | По умолчанию | Описание |
| ---------- | ------------ | -------- |
| `RLM_SANDBOX_MODE` | `process` | `process` — worker-процесс на сессию (production default, включается сам); `inline` — прежнее выполнение в MCP-процессе (диагностика/аварийный fallback, hard-kill таймаута НЕ гарантируется). Допустимы ТОЛЬКО эти два значения; иное — ошибка старта, а не откат к inline |
| `RLM_SANDBOX_START_TIMEOUT_SECONDS` | `60` | Timeout инициализации worker (холодный spawn + импорты + открытие индекса). НЕ равен execution timeout. При истечении `rlm_start` завершается ошибкой, процесс убивается, сессия не создаётся |
| `RLM_SANDBOX_KILL_GRACE_SECONDS` | `1` | Короткий grace между terminate и hard kill дерева процессов. `0` — немедленный kill |
| `RLM_SANDBOX_SHUTDOWN_DEADLINE_SECONDS` | `10` | **Один общий** deadline остановки ВСЕХ workers при shutdown сервера (не по 10с на каждого). Целое `1..60`; после истечения оставшиеся деревья получают немедленный force-kill без нового окна ожидания |
| `RLM_SANDBOX_MEMORY_MB` | `1024` | Per-worker потолок памяти: Windows — Job Object process memory limit; Linux — `RLIMIT_AS`; macOS/прочие POSIX — best effort. `0` — лимит отключён (warning в лог). Суммарный бюджет ≈ `RLM_MAX_SESSIONS × RLM_SANDBOX_MEMORY_MB` + память parent MCP + ОС/descendants; потолок ≠ фактический RSS — подбирайте обе переменные совместно под свои конфигурации |
| `RLM_SANDBOX_IPC_MAX_BYTES` | `4194304` | Максимальный размер одного IPC JSON-frame parent↔worker. Floor 256 KiB (init-ответ несёт снимок реестра хелперов). Действует в обе стороны: ответ worker крупнее лимита → worker убивается controlled + lazy restart; исходящий execute-frame крупнее лимита отклоняется родителем (`CodeTooLargeError`, worker остаётся жив) — это отдельный от `RLM_SANDBOX_MAX_CODE_CHARS` отказ |
| `RLM_SANDBOX_MAX_CODE_CHARS` | `1000000` | Код длиннее отклоняется родителем ДО отправки worker (controlled error, worker жив) |
| `RLM_SANDBOX_MAX_PROCESSES` | `16` | Windows Job Object active-process limit (worker + его descendants, включая `git` из `git_search`). `0` — отключить. POSIX `RLIMIT_NPROC` сознательно НЕ применяется (на ряде систем считается per-UID и задел бы соседние workers) |

Допустимые значения (любое нарушение — **понятная ошибка старта сервера**, а не тихая подстановка default).

Про пустую строку правила РАЗНЫЕ:

* `RLM_SANDBOX_MODE` — default подставляется, только если переменной **нет вообще**. Явно заданная пустая строка (`RLM_SANDBOX_MODE=`) — ошибка старта: иначе опечатка в `.env` молча отключила бы процессную изоляцию.
* числовые переменные — отсутствие переменной и пустая строка равнозначны и дают default.

| Переменная | Диапазон | Что означает `0` |
| ---------- | -------- | ---------------- |
| `RLM_SANDBOX_MODE` | только `process` \| `inline` | — |
| `RLM_SANDBOX_START_TIMEOUT_SECONDS` | `1..3600` | ошибка конфигурации |
| `RLM_SANDBOX_KILL_GRACE_SECONDS` | `0..60` | немедленный kill без grace |
| `RLM_SANDBOX_SHUTDOWN_DEADLINE_SECONDS` | `1..60` | ошибка конфигурации |
| `RLM_SANDBOX_MEMORY_MB` | `0` или `>= 16` | лимит отключён (warning при старте) |
| `RLM_SANDBOX_IPC_MAX_BYTES` | `>= 262144` | ошибка конфигурации |
| `RLM_SANDBOX_MAX_CODE_CHARS` | `>= 1000` | ошибка конфигурации |
| `RLM_SANDBOX_MAX_PROCESSES` | `0` или `1..1024` | лимит отключён |

Фактически применённые платформенные гарантии пишутся в `server.log` при старте каждого worker (`group=…`, `memlimit=…`). Если запрошенный `RLM_SANDBOX_MEMORY_MB > 0` применить не удалось, в лог идёт отдельный WARNING — потолок памяти не считается установленным молча. Текущий режим песочницы виден агенту в ответе `rlm_start` как `limits.sandbox_mode`.

Семантика timeout в `process`-режиме: deadline контролирует родитель; по истечении дерево процессов убивается независимо от того, что делает код (перехват `BaseException`, C-extension, catastrophic regex, блокирующий I/O). Возвращается частичный stdout, накопленный к моменту kill, с маркером `... [execution terminated after timeout; partial output]`; все переменные и кэши сессии теряются (`sandbox_state.state_lost=true`), следующий `rlm_execute` лениво поднимает чистое поколение worker (`sandbox_state.status="restarted"` в первом ответе). Лимиты `execute`/LLM-вызовов сессии при этом сохраняются.

Процессная изоляция — это application-level containment (hard-kill, отдельные namespace/память), **а не полноценный OS security boundary**: worker работает с правами пользователя сервиса, и после Python-escape ему потенциально доступны файлы/сеть/environment (включая LLM-credentials), разрешённые этому пользователю. OS-jail (отдельная учётная запись, ACL, read-only mounts, firewall/container policy) — ответственность оператора, см. [INSTALL.md](INSTALL.md).

Платформы: Windows и Linux — обязательные CI/release-gates; macOS — best effort (spawn/process-group без Job-эквивалента и без CI-runner).

## Лимиты анализа (effort / вызовы)

По умолчанию глубину выбирает сервер по тексту запроса (`effort="auto"`): `medium` для простых лукапов, `high` для многоаспектных задач. Эти переменные позволяют переопределить.

| Переменная | По умолчанию | Описание |
| ---------- | ------------ | -------- |
| `RLM_FORCE_EFFORT` | — (не задан) | Жёсткий замок глубины (`low`/`medium`/`high`/`max`): если задан — **перекрывает** и авто-выбор, и `effort` агента. По умолчанию НЕ задан → работает авто-выбор. Невалидное значение игнорируется (с warning). Меняет тир целиком (лимиты + guidance + ширина grep). Пример: `RLM_FORCE_EFFORT=high` — всегда полнота; `=medium` — всегда дешевле. |
| `RLM_MAX_EXECUTE_CALLS` | — (пресет тира) | **Server-default** числового лимита `rlm_execute` на выбранном тире (НЕ hard cap — напр. «остаться high, но 80» — фикс рестартов без смены глубины). Явный параметр тула `max_execute_calls` его перекрывает. Невалидное (≤0/не число) — игнорируется. |
| `RLM_MAX_LLM_CALLS` | — (пресет тира) | То же для `llm_query`/`llm_query_batched`. |

> Прецеденс effort: `RLM_FORCE_EFFORT` (если задан) > явный `effort` агента > `auto` (по запросу). Прецеденс числа: явный параметр тула > `RLM_MAX_*` (env) > пресет тира. Итог — в `response["effective_effort"]` и `response["limits"]`; при расхождении лимитов с пресетом стратегия начинается с баннера `== SERVER LIMIT OVERRIDE ==`. Изменение env требует рестарта MCP-сервера.

## Docker

Переменные для работы в Docker-контейнере.

| Переменная     | По умолчанию | Описание                                                                                                                                                                   |
| -------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_VERSION`  | —            | Версия пакета для установки (в `docker-entrypoint.sh`). Пусто или `latest` — авто-обновление из PyPI при каждом старте. Конкретная версия (напр. `1.6.2`) — `pip install ==version`, без проверки PyPI. Позволяет откатиться при сломанном релизе |
| `RLM_PATH_MAP` | —            | **Трансляция хостовых путей в контейнерные.** Формат: `хостовый_префикс:контейнерный_префикс`. Пример: `D:/Repos/1c:/repos`. Когда задана, пользователь может указывать хостовые пути при регистрации проектов, старте сессий и работе с индексами — сервер автоматически подменяет префикс. Без этой переменной нужно использовать контейнерные пути (`/repos/...`) |
| `RLM_UPDATE_INDEX_ON_START` | `0` | Обновлять ли индексы зарегистрированных проектов при старте контейнера (`docker-entrypoint.sh`, Stage 3). По умолчанию **выключено** (`0`): безусловное обновление на каждом старте дорого на Docker Desktop/Virtiofs (Windows) — даже no-op инкремент может занимать минуты на проект из-за медленного stat/хэширования по FS. Значение `1` — восстановить прежнее поведение (обновлять все индексы перед запуском сервера). Вне зависимости от флага индекс всегда можно обновить вручную: `rlm-bsl-index index update <path>` (или MCP-тул `rlm_index(action='update')`) |

## SQLite-индекс методов

Индекс опционален — создаётся командой `rlm-bsl-index index build <path>`. Подробнее — [INDEXING.md](INDEXING.md).

| Переменная                    | По умолчанию              | Описание                                                                                                                                    |
| ----------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_INDEX_DIR`               | см. precedence ниже       | Каталог хранения индексов. **Precedence (v1.9.2+):** ① если задан `RLM_INDEX_DIR` — используется он; ② иначе если задан `RLM_CONFIG_FILE` — `dirname(RLM_CONFIG_FILE)/index/` (для Windows-службы LocalSystem пишет рядом с config/logs/cache, а не в `system32`); ③ иначе — `~/.cache/rlm-tools-bsl/`. Внутри создаётся подпапка с хешем пути конфигурации, например: `<root>/a3f8b2c1/bsl_index.db`. При первом старте v1.9.2 legacy-индексы из `~/.cache/rlm-tools-bsl/<hash>/` автоматически переезжают в новый root |
| `RLM_INDEX_MAX_AGE_DAYS`      | `7`                       | Порог предупреждения о возрасте индекса (дни). Если индекс старше — статус `STALE_AGE`                                                      |
| `RLM_INDEX_SAMPLE_SIZE`       | `5`                       | Количество файлов для выборочной проверки свежести. `0` — отключить проверку                                                                |
| `RLM_INDEX_SAMPLE_THRESHOLD`  | `30`                      | Минимальное число модулей в индексе, при котором выполняется выборочная проверка                                                            |
| `RLM_INDEX_SKIP_SAMPLE_HOURS` | `24`                      | Если индекс моложе этого порога (часы), выборочная проверка пропускается — сразу `FRESH`                                                    |
| `RLM_GIT_DIRTY_TIMEOUT`       | `120`                     | Таймаут (секунды) best-effort git-команд детекта незакоммиченных правок (`git diff`/`ls-files` по рабочему дереву) в инкрементальном обновлении. Дефолт **120** выбран по натурным замерам: на медленной ФС (Docker Desktop / Virtiofs на Windows) детект по крупному CRLF-vs-LF дереву занимал ~97с — при меньшем пороге апдейт уходил бы в полный скан. Для здоровых репозиториев безвреден (детект завершается за секунды, далеко до потолка). На совсем больших/медленных конфигурациях можно поднять ещё. При невалидном значении используется 120. **Связано с EOL:** если рабочее дерево CRLF, а индекс LF (типично для 1С-репо под Windows + Docker), git перечитывает все файлы — лучше нормализовать концы строк (см. [INSTALL.md](INSTALL.md#вариант-b-docker)), тогда детект мгновенный и таймаут не важен |
| `RLM_GIT_SEARCH_TIMEOUT`      | `30`                      | Таймаут (секунды) одного вызова `git grep` в полнотекстовом поиске (`git_search` и git-ускоренный `safe_grep`). `git grep` по полной конфигурации (десятки тысяч файлов) отрабатывает за доли секунды, поэтому 30с — щедрый потолок, который всё же ограничивает патологический regex или зависшую ФС. При невалидном значении используется 30 |
| `RLM_CACHE_MAX_AGE_DAYS`      | `14`                      | Порог авто-очистки **кэша** BSL-файлов (`~/.cache/rlm-tools-bsl/` либо `dirname(RLM_CONFIG_FILE)/cache/`, если задан). При старте MCP-сервера удаляются подпапки проектов, не использовавшихся дольше этого срока. Значение `0` или отрицательное — очистка отключена. Активность проекта обновляется при каждом `rlm_start`, `rlm_index build/update/info`. **Миграция с v1.9.0**: при первом запуске v1.9.1 legacy-кэши зарегистрированных проектов (без маркера `last_used.txt`) получают свежий маркер и не удаляются. Зарегистрированные-но-забытые проекты чистятся на последующих запусках, когда маркер устареет. **BSL-индексы (`RLM_INDEX_DIR`) НЕ подпадают под эту очистку** — они дорого строятся; управляйте ими вручную через `rlm_index(action='drop')` |

## Реестр проектов

Файл `projects.json` хранит соответствие человекочитаемых имен проектов путям к каталогам исходников. Располагается **рядом с активным `service.json`**:

- Если задан `RLM_CONFIG_FILE=/etc/rlm-tools-bsl/service.json` -- реестр будет `/etc/rlm-tools-bsl/projects.json`
- Иначе -- `~/.config/rlm-tools-bsl/projects.json`

Управление реестром -- через MCP-тул `rlm_projects` (list/add/remove/rename/update). После регистрации проекта можно открывать сессии по имени: `rlm_start(project='My Config', query='...')`.

## Стратегия `rlm_start`

| Переменная           | По умолчанию | Описание                                                                                                                               |
| -------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_STRATEGY_MODE`  | `slim`       | Формат стратегии, возвращаемой `rlm_start`. **`slim`** (по умолчанию) — компактная маршрутная карта (на больших проектах без расширений ~6–9К символов / ~1.5–4К токенов; на конфигах с расширениями добавляются счётчики перехватов — детализация регулируется RLM_EXT_OVERRIDE_DETAIL, см. ниже): блоки `== HELP ==`, `== WORKFLOW (overview) ==`, `== DISAMBIGUATION (pointer) ==` + указатели на новый MCP-tool `rlm_help(topic=…|category=…|helpers=[…]|section=…)`, который выдаёт детальные рецепты, описания пар и тексты секций по запросу. **`full`** — legacy-формат (~16–23К символов / ~4–13К токенов): все Step 0–5, развёрнутый DISAMBIGUATION, расширенный STEP 4, полная таблица хелперов и BATCHING. В режиме `full` **MCP-тул `rlm_help` не регистрируется** на сервере и недоступен агенту — вся справка inline. Невалидное значение трактуется как `slim`. Внутрипесочничный `help('keyword')` (BSL-хелпер) работает в обоих режимах одинаково. **Когда переключать на `full`:** если на слабых моделях (Haiku, мелкие OSS) заметна регрессия качества анализа — попробуйте перезапустить сервер с `RLM_STRATEGY_MODE=full`. Изменение режима требует рестарта MCP-сервера (FastMCP кеширует список тулов). |
| `RLM_EXT_OVERRIDE_DETAIL` | `0` | Сколько строк поимённых перехватов расширений (`Объект: &Перед("Метод")`) включать в стартовую стратегию **суммарно по всем расширениям** (и в slim, и в full). По умолчанию `0` — только счётчики на расширение + указатель на `get_overrides('ИмяОбъекта')`/`find_ext_overrides()`. На extension-heavy конфигах (напр. УТ 11.5: 14 расширений) прежний поимённый дамп раздувал `rlm_start` до ~64K символов / ~37K токенов в каждой сессии. Значение `>0` возвращает ограниченную детализацию (единый глобальный бюджет строк). |
| `RLM_EXT_LIST_CAP` | `20` | Порог числа расширений, выше которого **агент-facing** представления списка расширений ужимаются до top-N по числу overrides. Затрагивает только три отображения в ответе `rlm_start`: `warnings` (короткая сводка вместо join всех путей), поле `extension_context.nearby_extensions` (top-N + companion-поля `nearby_extensions_truncated`/`nearby_extensions_total`/`nearby_extensions_shown`/`extensions_hint`) и блок «CRITICAL — EXTENSIONS DETECTED» в стратегии (top-N + строка `+K more`). При `N ≤ cap` поведение байт-в-байт прежнее. `<=0` (в т.ч. `-1`) — без лимита; невалидное значение → дефолт `20`. На extreme-extension конфигах (напр. 155 расширений / 604 overrides) полный список раздувал `rlm_start` выше токен-лимита инструмента. **НЕ влияет** на поиск, на внутренний список объектов расширений и на питание песочницы (`find_module`/`find_attributes` по всем расширениям работают как раньше). Полный список расширений всегда доступен через `detect_extensions()` (перехваты — `get_overrides()`, отдаёт первые 200 + `total`/`truncated`). |

## Диагностика

| Переменная        | По умолчанию | Описание                                                                                                                              |
| ----------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_LOG_HELPERS` | —            | Режим логирования хелперов. По умолчанию логируются только вызовы дольше 0.1 сек. Значение `all` — логировать все вызовы с таймингами |
| `RLM_LOG_EXECUTE_CODE` | `300`   | Логировать ли сам код агента (сам «запрос» — вызовы хелперов с параметрами) в строке-событии `rlm_execute` в поле `code=<...>`. Нужно для последующего анализа запросов и понимания, под какие из них стоит доработать хелперы. **По умолчанию ВКЛючено** с cap 300 символов. Переносы строк схлопываются в `⏎`, чтобы событие осталось одной строкой лога (удобно грепать/парсить); превышение cap обрезается с многоточием `…`. Значения: положительное целое `N` — cap в `N` символов; `1`/`true`/`on`/`yes`/`all` — дефолтный cap; `0`/`false`/`off`/`no` (и `N<=0`) — выключить. Код может содержать имена объектов конфигурации (в т.ч. кириллицу) — держите `server.log` соответствующим политике доступа |
| `RLM_LOG_RETENTION_DAYS` | `20` | На старте службы/сервера удалять из `server.log` записи старше N дней, чтобы лог не распухал. Лог append-only и хронологический: находится первая строка с меткой `YYYY-MM-DD HH:MM:SS` не старше `сегодня − N дней`, и всё до неё срезается (строки без метки — из stderr-редиректа службы — группируются с блоком, в котором стоят; если распознаваемых меток нет вовсе, лог не трогается). Перезапись атомарная, до открытия файла на запись. `0` или отрицательное — отключить. Ротационные бэкапы `server.log.1..3` (по 5 МБ) не трогаются — они и так ограничены размером |
