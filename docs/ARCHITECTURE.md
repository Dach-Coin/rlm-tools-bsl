# Как работает (под капотом)

## Пять инструментов MCP

| Инструмент                      | Что делает                                                                                                           |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `rlm_projects(action, ...)`     | Управление реестром проектов: `list`, `add`, `remove`, `rename`, `update`. Связка имя → путь к исходникам. Все мутирующие операции требуют `password`; смена пароля — через `clear_password` + повторный `update(password=...)` |
| `rlm_index(action, ...)`        | Управление SQLite-индексом методов: `build` (полная сборка), `update` (инкрементальное обновление), `info` (статистика), `drop` (удаление). build/update выполняются в фоне (`{"started": true}`), статус через info. build/update/drop требуют зарегистрированный проект с паролем (CLI `rlm-bsl-index` работает без пароля). С v1.21.0 инкрементальный `update` держит граф вызовов консистентным со свежей сборкой (пере-резолв привязок `callee_key` при изменении общих модулей), без пересборки индекса. С v1.32.0 **новое** построение индекса на формате, отличном от cf/edt, через MCP отклоняется до постановки фоновой job — подтвердить заведомо неполную сборку может только человек в терминале (`rlm-bsl-index index build <path> --allow-unsupported-format`) |
| `rlm_start(path, query)`        | Открывает сессию на каталоге исходников. Определяет формат (CF/EDT), строит индекс BSL-файлов, возвращает session_id |
| `rlm_execute(session_id, code)` | Выполняет Python-код в песочнице. Данные остаются на сервере, в контекст попадает только stdout                      |
| `rlm_end(session_id)`           | Закрывает сессию, освобождает ресурсы                                                                                |

## Что происходит при `rlm_start`

1. **Определение формата** — сканирует структуру каталога и определяет: CF (Конфигуратор, каталоги `Ext/`), EDT (1C:EDT, файлы `.mdo`), или смешанный
2. **Классификация поддержки** (v1.32.0) — отдельно от формата решается, наш ли это формат вообще. Признак — **валидный дескриптор** CF (`Configuration.xml` с корнем `{MDClasses}MetaDataObject` и первым дочерним `Configuration`) или EDT (`Configuration/Configuration.mdo` с корнем `{mdclass}Configuration`); дескриптор ищется в корне, прямом подкаталоге или через один каталог-обёртку (`cfe/ExtA/…`), читается **префиксно** (два первых start-события `iterparse`) и не парсится целиком. Одного имени файла недостаточно: чужой `docs/Configuration.xml` гейт не обходит. Результат уезжает в ответ полем `source_support`:
   - `supported` — поведение сессии без изменений;
   - `foreign_with_bsl` — чужая раскладка, но `.bsl` есть: сессия работает, BSL-хелперы остаются, первым идёт предупреждение (и в `warnings[0]`, и в начале `strategy`), результат объявляется best-effort;
   - `foreign_no_bsl` — чужая раскладка без единого `.bsl`: **generic-режим**, BSL-хелперы в песочницу не загружаются вовсе, стратегия своя (`build_generic_strategy`) и перечисляет только базовые файловые хелперы. Нумерация строк `read_file`/`read_files`/`grep_read` сохраняется.

   Классификация выполняется на **каждом** `rlm_start`, включая index fast path (индекс мог быть собран до появления гейта), поэтому она обязана быть дешёвой: листинги каталогов только уровней 0–1, кандидаты уровня 2 — точечные `open()`. На боевых cf/edt — единицы миллисекунд.
3. **Построение индекса** — находит все `.bsl` файлы, для каждого определяет: категорию (`Documents`, `Catalogs`, `CommonModules`...), имя объекта, тип модуля (`ObjectModule`, `ManagerModule`, `FormModule`...)
4. **Дисковый кэш** — индекс сохраняется на диске в `%USERPROFILE%\.cache\rlm-tools-bsl\<хэш_пути>\file_index.json` (Windows) или `~/.cache/rlm-tools-bsl/<хэш_пути>/file_index.json` (Linux/macOS). При повторном запуске на том же каталоге (если количество .bsl файлов не изменилось) — индекс загружается мгновенно
5. **Детектирование расширений** — XML-парсинг `Configuration.xml` / `Configuration.mdo` для определения, является ли каталог основной конфигурацией или расширением. Автоматическое сканирование соседних каталогов (1-2 уровня вверх) на наличие расширений или основной конфигурации. Запуск на standalone-расширении поддерживается (is_extension=True). Запуск на расширении внутри контейнера (напр. `src/cfe/Ext1/`) — не поддерживаемый сценарий; рекомендуется запускать на основной конфигурации, расширения из соседних каталогов (включая контейнеры `src/cfe/` с несколькими расширениями) обнаруживаются автоматически
6. **Хелперы** — в песочницу добавляются BSL-специфичные функции для навигации по коду (в generic-режиме — только базовые файловые)
7. **Сессионные кэши** — в рамках одной сессии кэшируются: содержимое файлов (LRU, до 500 файлов), результаты `extract_procedures()` (по пути файла), результаты grep (LRU, до 100 запросов), списки файлов-кандидатов для `find_callers_context()`. Благодаря этому повторные вызовы при построении графа вызовов работают мгновенно — файлы не перечитываются и не парсятся заново

## Таймауты и безопасность

### Процессная изоляция (v1.29.0, `RLM_SANDBOX_MODE=process`)

Код агента выполняется в **отдельном sandbox-worker-процессе на каждую сессию**:

```text
MCP server (родительский процесс)
  ├─ Session A → Sandbox worker A → Sandbox A + namespace A + IndexReader A
  ├─ Session B → Sandbox worker B → Sandbox B + namespace B + IndexReader B
  └─ Session C → Sandbox worker C → Sandbox C + namespace C + IndexReader C
```

Worker живёт от успешного `rlm_start` до `rlm_end`/TTL-эвикции/аварии/остановки сервера — переменные и кэши сессии сохраняются между `rlm_execute` внутри worker. Это даёт:

- **stdout физически разделён процессами** — параллельные `rlm_execute` разных сессий не могут смешать вывод (в v1.28 такая гонка была воспроизведена: `redirect_stdout` подменял глобальный `sys.stdout` общего процесса);
- **hard wall-clock kill**: авторитетный deadline (по умолчанию 45с, `execution_timeout_seconds` в `rlm_start`, ≤300с) контролирует родитель. По истечении дерево процессов worker уничтожается целиком — Windows Job Object (`KILL_ON_JOB_CLOSE`), POSIX process group (`setsid`+`killpg`) — независимо от того, что делает код: перехват `BaseException`, зависший C-extension, catastrophic regex, блокирующий I/O, запущенные дочерние процессы;
- **частичный stdout**: вывод пишется worker-ом напрямую в shared-буфер с публикацией по целым UTF-8 символам, поэтому всё напечатанное до kill возвращается агенту с маркером `... [execution terminated after timeout; partial output]`;
- **потеря состояния — явная**: после kill все переменные/кэши worker потеряны; ответ несёт machine-readable `sandbox_state={status:"terminated", reason:..., state_lost:true, restart:"on_next_execute"}`, следующий `rlm_execute` лениво поднимает чистое поколение (`sandbox_state.status="restarted"` в его первом ответе). Счётчики execute/LLM-вызовов сессии живут в родителе и сохраняются;
- **crash/OOM worker не роняет MCP-сервер** — сессия получает controlled error и lazy restart;
- **лимиты на worker**: память (`RLM_SANDBOX_MEMORY_MB`, Job Object / `RLIMIT_AS`), размер кода и IPC-фреймов; вывод ограничивается в момент `write`, а не после выполнения.

IPC parent↔worker — только UTF-8 JSON-фреймы с protocol version/allowlist типов/request id/generation и лимитом размера (`send_bytes`/`recv_bytes(maxlength)`); pickle для runtime-сообщений от запущенного worker не используется. Raw fd 0/1/2 worker отвязаны от родителя до выполнения любых команд — escaped-код не может испортить MCP stdio framing.

Режим `inline` (`RLM_SANDBOX_MODE=inline`) сохраняет прежнее выполнение в основном процессе — только для диагностики и аварийного восстановления. stdout-гонка закрыта и там (глобальная сериализация всех inline-execute), но hard-kill НЕ гарантируется: используется прежний fallback-таймаут — `SIGALRM` на Unix, `threading.Timer` + `PyThreadState_SetAsyncExc` на Windows/не-main-thread, — который код может пережить. Автоматического fallback `process` → `inline` нет; невалидный `RLM_SANDBOX_MODE` — ошибка старта сервера.

### Параллельность и бюджет памяти

Каждая сессия — это отдельный worker-процесс, поэтому сессии изолированы по namespace и памяти, а параллельные `rlm_execute` разных сессий физически идут в разных процессах. Модель памяти при этом устроена так, что «поднять лимиты» почти никогда не нужно, а интуиция про них легко даёт осечку:

- **`RLM_SANDBOX_MEMORY_MB` — это ПОТОЛОК, а не резервирование и не floor.** Worker (Job Object process memory limit на Windows / `RLIMIT_AS` на Linux) занимает ровно столько, сколько реально нужно коду сессии: namespace + собственный `IndexReader` + прочитанные тела файлов. При потолке 1024 и 512 фактический RSS при обычной нагрузке одинаков. **Понижение потолка нормальную память НЕ уменьшает** — оно лишь сдвигает порог, на котором убивают ОДНУ разросшуюся сессию: утечка или огромная аллокация ловит `MemoryError`/kill раньше, чем утащит хост в swap/OOM. Это тугой предохранитель против одного патологического сеанса, а не рычаг суммарного расхода.
- **Суммарный расход контролирует число воркеров, а не потолок.** Worst-case потолок всего сервера ≈ `RLM_MAX_SESSIONS × RLM_SANDBOX_MEMORY_MB + память parent` — но это ВЕРХНЯЯ граница, а не факт: реальный RSS почти всегда кратно ниже. Чтобы ограничить общий расход на слабом хосте, снижают **`RLM_MAX_SESSIONS`** (меньше одновременных воркеров = меньше параллельных RSS), а не память на воркер.
- **Порядок величин.** Даже полный разбор тяжёлого документа ERP (десятки модулей, сотни методов) держит в namespace worker единицы МБ сырых тел + разобранные структуры; `IndexReader` добавляет десятки–сотни МБ рабочего набора SQLite (страницы кешируются по требованию, а не грузятся целиком). Дефолтный потолок 1 ГБ/воркер оставляет большой запас — его имеет смысл при желании ПОНИЖАТЬ (тугой предохранитель), а не повышать.
- **Что реально едет по IPC.** `execute_result`-фрейм несёт только `error` + ИМЕНА переменных + `helper_calls` + hints — НЕ stdout (он публикуется в отдельный shared-буфер) и НЕ ЗНАЧЕНИЯ переменных. Крупный результат хелпера остаётся в namespace worker и IPC не пересекает; `RLM_SANDBOX_IPC_MAX_BYTES` (4 МиБ) ограничивает лишь размер одного сообщения и на практике недостижим — кроме патологии (тысячи `helper_calls` в одном execute или гигантский traceback, который к тому же авто-обрезается под фрейм).

### Честная граница безопасности

AST-гейт и урезанные builtins песочницы — это БАЗОВАЯ защита (defense-in-depth), а не
полноценная security-граница: она снижает СЛУЧАЙНЫЙ вред и закрывает дешёвые/известные
способы побега (запись файлов, сеть, опасные импорты, классический escape-гаджет через
dunder/интроспекцию, vars()/globals(), operator.attrgetter, license/credits/copyright,
мутация атрибутов объектов obj.attr=…).

Процессная изоляция v1.29.0 добавляет application-level containment (отдельные
namespace/память, hard-kill, resource limits), но **не является OS security boundary**:
worker работает с правами пользователя сервиса, и после успешного Python-escape ему
потенциально доступны файлы, сеть и environment (включая LLM-credentials), разрешённые
этому пользователю. Worker и parent под одним OS identity не образуют adversarial jail.
Для сильной защиты применяйте OS-jail средствами оператора: отдельная учётная запись,
read-only ACL на исходники, firewall/container policy — см. раздел «OS hardening» в
[INSTALL.md](INSTALL.md).

**Двухуровневый TTL сессий:** idle-сессии (без единого `execute`-вызова, `calls=0`) автоматически закрываются через 10 минут (`RLM_SESSION_TIMEOUT_IDLE`). Активные сессии (`calls>0`) живут до 30 минут (`RLM_SESSION_TIMEOUT_ACTIVE`). Единая переменная `RLM_SESSION_TIMEOUT` переопределяет оба значения (backward compat). Это защищает от «осиротевших» сессий, которые модель открыла, но не использовала.

Реальный пример на конфигурации 1С:ERP (23 000+ файлов). Задача: найти все экспортные методы регистра сведений `ГрафикПлатежей` и построить граф вызовов.

```

# Сессия открыта, индекс 23K+ файлов загружен из кэша

    modules = find_module("ГрафикПлатежей")

    exports = find_exports(reg[0]['path'])
    # Вывод: 11 экспортных методов (ManagerModule)

    for proc in export_names:

            L2 = find_callers_context(c1['caller_name'], module_hint=c1['object_name'])

    # Таймаут на инфраструктурных методах (ПроведениеДокументов → 150+ документов)

    # Дослать оставшиеся 3 метода — кэши прогреты, мгновенно
    # Вывод: граф для оставшихся методов
```

## Совместное использование с RAG

В rlm-tools-bsl не встроены вызовы внешних RAG/MCP-серверов — и это осознанное решение. Инструмент остаётся автономным и не зависит от внешней инфраструктуры.

При этом AI-агент (Claude Code, Cursor, Windsurf) **уже является оркестратором**: он видит все подключённые MCP-серверы и сам комбинирует их вызовы в рамках одной задачи. Встраивать один инструмент в другой — значит делать за агента то, что он и так умеет.

Пример комбинированного workflow:
```
Агент видит MCP-серверы:
  - rlm-tools-bsl  (анализ исходников на лету, граф вызовов)
  - 1c-metacode    (индексированные метаданные, семантический поиск)

Агент получает задачу: "Как работает механизм оплаты?"

Шаг 1: 1c-metacode → search_metadata("Оплат") → список объектов
Шаг 2: rlm-tools-bsl → find_module("ОплатаПоставщику") → модули, код
Шаг 3: rlm-tools-bsl → find_callers_context("РассчитатьГрафикОплаты") → граф вызовов
        (NB: у ОбработкаПроведения вызов от платформы в граф не попадает, поэтому пустые
         callers — норма, а не мёртвый код; явный BSL-вызов обработчика, если он есть,
         хелпер всё же покажет)
Шаг 4: 1c-metacode → search_code("РассчитатьГрафик") → дополнительный контекст из индекса
```

Оба инструмента работают параллельно, каждый в своей зоне: rlm-tools-bsl — анализ кода на лету без подготовки, RAG — семантический поиск и структурные связи из индекса.
