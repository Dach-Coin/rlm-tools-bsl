# Индекс методов BSL

## 1. Что такое индекс методов

Индекс методов — это предварительно построенная SQLite-база, содержащая таблицу всех процедур и функций кодовой базы 1С, а также (опционально) эвристический граф вызовов между ними. Индекс позволяет мгновенно отвечать на вопросы типа "какие методы есть в модуле?", "кто вызывает эту функцию?", "какие экспортные процедуры у объекта?" — без повторного чтения файлов с диска.

### Аналоги и сравнение

| Возможность                       | CodeRLM                | Aider RepoMap                  | GitHub BM25          | **rlm-tools-bsl**                                                                                        |
| --------------------------------- | ---------------------- | ------------------------------ | -------------------- | -------------------------------------------------------------------------------------------------------- |
| Таблица символов (методы/функции) | tree-sitter → JSON API | ctags / tree-sitter            | —                    | regex-парсинг → SQLite `methods` (569K методов ERP)                                                      |
| Граф вызовов                      | нет                    | «файл → символ» + PageRank     | нет                  | эвристический regex → SQLite `calls` (4.5M рёбер ERP). PageRank — Future, данные есть                    |
| Полнотекстовый поиск              | нет                    | нет                            | BM25 (Elasticsearch) | FTS5 trigram + BM25, встроен в SQLite (`search_methods`)                                                 |
| Метаданные конфигурации           | нет                    | нет                            | нет                  | `index_meta` (имя, версия, формат, роль), 17 таблиц метаданных (ES/SJ/FO/HTTP/WS/XDTO/synonyms/regions/headers/overrides/forms/attributes/predefined и др.) |
| Прозрачная интеграция             | отдельный API          | карта для промпта              | отдельный сервис     | хелперы автоматически ускоряются при наличии индекса, fallback на live-парсинг                           |
| Инкрементальное обновление        | нет                    | полная перестройка             | нет                  | `index update` — mtime/size дельта, git-ускорение при наличии .git                    |
| Зависимости                       | Rust + tree-sitter     | tree-sitter / ctags + networkx | Elasticsearch        | чистый Python + SQLite (stdlib), ноль внешних зависимостей                                               |
| Целевой язык                      | 10+ языков             | 10+ языков                     | любой                | заточен под BSL/1С (regex-грамматика, CF/EDT форматы, XML-метаданные)                                    |

**CodeRLM** — Rust-сервер с tree-sitter, строит таблицу символов. У нас аналогичная идея, но без tree-sitter (нет грамматики для BSL), парсим regex-ом.

**Aider RepoMap** — граф «файл → символ» с PageRank для ранжирования важности. У нас таблица `calls` — тот же граф, но в SQL. PageRank пока не делаем, данные для него уже есть.

**BM25 / keyword search** — GitHub выбрал BM25 вместо векторных эмбеддингов для поиска по коду. У нас FTS5 с trigram-токенайзером — подстроковый поиск по именам методов с BM25-ранжированием, встроенный в SQLite.

**Чем отличаемся:** Без tree-sitter, networkx, embeddings или внешних зависимостей. Чистый Python + SQLite (stdlib). Заточен под BSL/1C. Индекс полностью опциональный — без него всё работает, с ним — мгновенно. E2E-тесты показали снижение MCP-вызовов на 33% (Sonnet) и кратное улучшение качества для слабых моделей (Minimax: с ошибок до чистого отчёта).

### Наличие `.git` существенно прокачивает поиск

Если каталог исходников — git-рабочее-дерево (есть папка `.git`), автоматически подключается движок `git grep` как **новый бэкенд полнотекстового поиска** (хелпер `git_search`). Это закрывает системную дыру: SQLite-индекс и FTS5 ищут только по **именам** (методов, объектов, синонимов), а `git grep` за доли секунды ищет **любую подстроку по всем отслеживаемым файлам**, включая сырой `.xml`/`.mdo` (формы, права ролей, СКД, ConfigDumpInfo), тела процедур, строковые литералы и тексты запросов — то, что обычным хелперам недоступно. Ищется **текущее состояние на диске** (включая незакоммиченные правки и новые untracked-файлы); не ищется только `.gitignore`'d. Фича opt-in (только под git), не зависит от схемы индекса и не требует его перестройки. Требуется установленный `git`: **в Docker-образе он уже установлен** (явной строкой в `Dockerfile`, нужен и для git-ускорения инкрементальной индексации), поэтому `git_search` в контейнере работает без доп. настройки; на хосте Windows/Linux нужен `git` в `PATH` (в дев-окружении 1С он почти всегда есть).

## 1.1. Путь к исходникам

Путь, передаваемый в `rlm-bsl-index index build <path>` и в `rlm_start(path=...)`, должен указывать на **каталог, где реально лежат исходники конфигурации** — т.е. на тот уровень, где начинаются папки `Documents/`, `Catalogs/`, `CommonModules/` и т.д.

Примеры правильных путей:

| Формат | Структура репозитория                                            | Путь для индексации       |
| ------ | ---------------------------------------------------------------- | ------------------------- |
| EDT    | `D:\Projects\erp_edt\src\` (внутри `Documents/`, `Catalogs/`...) | `D:\Projects\erp_edt\src` |
| CF     | `D:\Projects\bgu\src\cf\` (внутри `Documents/`, `Catalogs/`...)  | `D:\Projects\bgu\src\cf`  |

Типичная ошибка — указать корень репозитория (`D:\Projects\erp_edt`) вместо подкаталога с исходниками (`D:\Projects\erp_edt\src`). В этом случае rlm-tools-bsl не найдёт `.bsl`-файлы или найдёт их по неправильным относительным путям.

> **Подсказка:** если внутри указанного каталога сразу видны папки `Documents`, `Catalogs`, `CommonModules` — путь правильный.

## 1.2. Поддерживаемые форматы исходников

Официально поддерживаются выгрузка Конфигуратора (cf) и проект 1С:EDT (edt),
включая расширения и контейнеры с одним уровнем обертки.

| Исходники | rlm_start | index build |
| --- | --- | --- |
| CF/EDT | Без изменений | Без изменений |
| Чужой формат, .bsl есть | Предупреждение, best-effort по тексту BSL | CLI требует подтверждение; MCP отказывает |
| Чужой формат, .bsl нет | Только базовые файловые хелперы | Отказ |

CLI-флаг `--allow-unsupported-format` существует только у `index build`.
Он подтверждает построение заведомо неполного индекса и не помогает, если .bsl нет.

Признаком поддерживаемого формата является валидный дескриптор CF
(`Configuration.xml`) или EDT (`Configuration/Configuration.mdo`), а не одно
только имя файла. Дескриптор ищется в корне, прямом подкаталоге или через один
каталог-обертку.

## 2. Включение и настройка

Признак «включённости» индекса — не переменная окружения, а наличие файла `bsl_index.db` в каталоге хранения. Индекс создаётся командой `rlm-bsl-index index build <path>`. Если файл `bsl_index.db` существует — хелперы автоматически используют его для ускорения. Если файла нет — всё работает как раньше, без индекса.

> **Миграция с `method_index.db`:** при первом обращении к индексу файл `method_index.db` автоматически переименовывается в `bsl_index.db` (ленивая миграция). Если переименование невозможно (файл занят другим процессом) — используется старое имя как fallback, индекс работает без перебоев. Повторная попытка переименования произойдёт при следующем обращении.

Поведение индекса настраивается переменными окружения:

| Переменная                    | По умолчанию              | Описание                                                                                                                                                                                                                                                  |
| ----------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RLM_INDEX_DIR`               | см. ниже                  | Каталог хранения индексов. **Precedence (v1.9.2+):** ① `RLM_INDEX_DIR` — явный override; ② `dirname(RLM_CONFIG_FILE)/index/` если задан `RLM_CONFIG_FILE` (для Windows-службы это пишет рядом с config/logs/cache, а не в `system32`); ③ `~/.cache/rlm-tools-bsl/` (Linux/macOS desktop, Windows desktop). Внутри создаётся подкаталог с хешем пути конфигурации, например: `<root>/a3f8b2c1d4e5/bsl_index.db` |
| `RLM_INDEX_MAX_AGE_DAYS`      | `7`                       | Порог предупреждения о возрасте индекса (дни). Если индекс старше — статус `STALE_AGE`                                                                                                                                                                    |
| `RLM_INDEX_SAMPLE_SIZE`       | `5`                       | Количество файлов для выборочной проверки свежести. `0` — отключить проверку                                                                                                                                                                              |
| `RLM_INDEX_SAMPLE_THRESHOLD`  | `30`                      | Минимальное число модулей в индексе, при котором выполняется выборочная проверка                                                                                                                                                                          |
| `RLM_INDEX_SKIP_SAMPLE_HOURS` | `24`                      | Если индекс моложе этого порога (часы), выборочная проверка пропускается                                                                                                                                                                                  |

Переменные можно задать в `.env` файле или в окружении системы.

### Расположение индекса при установке как Windows-служба

Начиная с v1.9.2, если сервер запущен как Windows-служба под LocalSystem (стандартный сценарий `rlm-tools-bsl service install --env <path>`), индексы автоматически пишутся в `dirname(RLM_CONFIG_FILE)/index/`, рядом с `config/logs/cache`. До v1.9.2 индексы уезжали в профиль LocalSystem (`C:\Windows\System32\config\systemprofile\.cache\rlm-tools-bsl\`) и фактически терялись при следующем апгрейде службы.

**Авто-миграция при первом старте v1.9.2.** Если в legacy-локации (`~/.cache/rlm-tools-bsl/<hash>/`) обнаруживаются папки с `bsl_index.db` или `method_index.db`, и новый root отличается (есть `RLM_CONFIG_FILE` без явного `RLM_INDEX_DIR`), такие папки автоматически переезжают в новый root. В логах одна строка: `migrate_legacy_index_root: migrated_legacy_index_dirs=N to=<new_root>`. На последующих запусках операция NOOP. Идемпотентна, не перезаписывает уже существующий индекс в целевой локации, не трогает legacy при заданном `RLM_INDEX_DIR` (явный пользовательский override уважается).

Покрытые точки запуска: server.py (startup), docker-entrypoint.sh (перед auto-update индексов зарегистрированных проектов), CLI `rlm-bsl-index index build|update|info|drop`.

### Docker-рекомендация для `RLM_CONFIG_FILE`

В дефолтном `docker-compose.example.yml` `RLM_CONFIG_FILE` **не задан**: индексы лежат в `/home/rlm/.cache/rlm-tools-bsl/` (volume `rlm-index-cache`), поведение прежнее. Если же вы задаёте `RLM_CONFIG_FILE` явно (нестандартный сетап), то без `RLM_INDEX_DIR` индексы уедут в `dirname(RLM_CONFIG_FILE)/index/` — обычно это volume `rlm-config`, что нежелательно (медленнее, смешивается с конфигом). Рекомендация: либо НЕ задавайте `RLM_CONFIG_FILE` в Docker, либо явно задайте `RLM_INDEX_DIR=/home/rlm/.cache/rlm-tools-bsl`, чтобы индексы остались в volume `rlm-index-cache`.

## 3. MCP-тул `rlm_index`

Управление индексом из AI-клиента через MCP-протокол, без доступа к терминалу. Отличия от CLI: `build`, `update` и `drop` требуют зарегистрированный проект с паролем; параметр `path` для этих действий запрещён (только `project`). `info` работает и по `path`, и по `project`.

| Действие | Описание | Пример |
|----------|----------|--------|
| `build`  | Полная пересборка индекса (требует пароль) | `rlm_index(action="build", project="ERP", confirm="...")` |
| `update` | Инкрементальное обновление (требует пароль) | `rlm_index(action="update", project="ERP", confirm="...")` |
| `info`   | Статистика индекса | `rlm_index(action="info", project="ERP")` |
| `drop`   | Удалить индекс (требует пароль) | `rlm_index(action="drop", project="ERP", confirm="...")` |

Для `info` вместо `project` можно указать `path`. Опции build: `no_calls`, `no_metadata`, `no_fts`, `no_synonyms`.

### Пароль проекта для управления индексами

Действия `build`, `update` и `drop` через MCP требуют зарегистрированный проект с паролем. Параметр `path` для этих действий через MCP запрещён — только `project`.

При вызове без пароля сервер возвращает `approval_required: true` с просьбой запросить пароль у пользователя. Модель должна показать сообщение и дождаться ввода пароля, затем повторить вызов с `confirm=<пароль>`.

Пароль обязателен при регистрации проекта:

```
rlm_projects(action="add", name="ERP", path="D:\\Bases\\ERP", password="...")
```

Проект без пароля — build/update/drop через MCP заблокированы. Все мутирующие операции с реестром (remove/update/rename) также требуют текущий пароль (`password`). CLI-команда `rlm-bsl-index` работает без пароля.

**Зачем это нужно:** при E2E-тестировании слабые модели (Grok Code Fast 1, Kilo Auto) при обнаружении отсутствующего индекса самостоятельно вызывали `rlm_index(action='build')`, не спрашивая пользователя. Построение занимает 5-10 минут и блокирует I/O сервера. Пароль гарантирует, что только человек решает, когда строить индекс — модель не знает пароль заранее и не может обойти проверку.

### Блокировка параллельных сборок (build lock)

При запуске `build` или `update` сервер захватывает эксклюзивную файловую блокировку (`bsl_index.lock` рядом с БД). Если другой процесс уже строит индекс для этого же пути — возвращается ошибка `RuntimeError` вместо повреждения БД. Блокировка реентрантна **в рамках одного потока** (последовательные `build` + `update`, и рекурсивный `update → build` при восстановлении): другой **поток** того же процесса получает `RuntimeError` так же, как другой процесс — иначе два потока могли бы одновременно перестраивать одну БД «на месте» (v1.26.0). Реентрантность считается по owner-thread-id + depth; OS-блокировка (`msvcrt.locking` на Windows, `fcntl.flock` на Linux) и lock-файл снимаются только при выходе из внешнего захвата (depth → 0) и автоматически освобождаются при аварийном завершении процесса.

### Пересборка на месте (in-place rebuild, v1.26.0)

Полная пересборка (`build`) **не удаляет и не переименовывает** файл БД в штатном пути — на Windows `unlink`/`rename` под открытым read-only `IndexReader` падает `PermissionError`. Вместо этого схема очищается **на месте** (DROP всех объектов кроме `index_meta` → пересоздание из `_SCHEMA_SQL` → populate) под маркером незавершённости `index_meta.build_in_progress=1`. Маркер ставится **до** деструктивных операций и снимается **только** после успешного `ANALYZE`/`VACUUM` (единый success-gate). Пока маркер стоит, индекс считается `MISSING` для `rlm_start`/`check_index_*`, `incomplete` для CLI/MCP `info` и `get_index_info()` — новые сессии его не поднимают; `update` на недострое делает полную пересборку (восстановление). `unlink` остаётся **только** для self-healing битого/несовместимого файла (на нём живого reader быть не может). Конкурентный старый reader во время пересборки деградирует к пустым результатам (`_transient_safe`-обёртки), **не падает**, и самовосстанавливается по завершении. **Честная граница:** билд делает множество коммитов, единая атомарная транзакция нереалистична — concurrent-запрос в середине пересборки может вернуть частичные/пустые данные; внешние читатели не координируются (рекомендуется не запускать пересборку параллельно активным запросам). `drop` (CLI/MCP) по-прежнему делает `unlink` — «удалить индекс при живой сессии» на Windows останется `PermissionError` (известное ограничение, не ломает поиск).

### Фоновое построение

При вызове через MCP построение и обновление индексов выполняется в фоне:

```
rlm_index(action="build", project="ERP", confirm="пароль")
→ {"started": true, "action": "build", "project": "ERP", "message": "..."}
```

Проверка статуса:
```
rlm_index(action="info", project="ERP")
→ {..., "build_status": "building", "build_elapsed": 45.2}
→ {..., "build_status": "done", "build_result": {...}}
→ {..., "build_status": "error", "build_error": "..."}
```

Повторный запуск build/update на тот же проект заблокирован пока предыдущий не завершится. CLI-команда `rlm-bsl-index` по-прежнему работает синхронно.

Фоновый поток (`daemon=False`) не завершается при shutdown сервера — ожидает окончания сборки, чтобы не потерять полусобранный индекс. Данные `build_status` хранятся в памяти (in-memory) и недоступны после перезапуска сервера.

## 4. CLI-команды

### Полное построение

```bash
rlm-bsl-index index build <path> [--no-calls] [--no-metadata] [--no-fts] [--no-synonyms]
```

Сканирует все `.bsl`-файлы в `<path>`, извлекает процедуры/функции и (по умолчанию) эвристический граф вызовов. Дополнительно парсит XML-метаданные конфигурации и строит FTS5-индекс для полнотекстового поиска.

> **Шум графа вызовов.** Голые (unqualified) обращения к зарезервированным платформенным глобалам (`Сообщить`, `НСтр`, `Формат`, `НачатьТранзакцию`, `Новый Структура(` и т.п. — 105 имён) исключаются из графа: у них нет метода-цели в коде конфигурации, для навигации это нерелевантный балласт (~27% таблицы `calls`). Квалифицированные `Модуль.Метод(` не затрагиваются. Существующие индексы доочищаются разово при первом `build`/`update`.

Флаги:
- `--no-calls` — отключает построение графа вызовов (значительно ускоряет сборку)
- `--no-metadata` — отключает парсинг таблиц метаданных (EventSubscriptions, ScheduledJobs, FunctionalOptions, HTTPServices, WebServices, XDTOPackages, FormElements)
- `--no-fts` — отключает построение FTS5-индекса полнотекстового поиска
- `--no-synonyms` — отключает построение таблицы синонимов объектов (`object_synonyms`)

### Инкрементальное обновление

```bash
rlm-bsl-index index update <path>
```

Обновляет только изменённые файлы (по mtime+size). Требует предварительно построенного индекса.

Пример:

```bash
$ rlm-bsl-index index update D:\ERP\src
Инкрементальное обновление: D:\ERP\src

Обновлено за 1.2 сек
  Добавлено: 0
  Изменено:  3
  Удалено:   0
```

### Информация и статус

```bash
rlm-bsl-index index info <path>
```

Показывает статистику индекса и проверяет его актуальность.

### calls

Эвристический граф вызовов (regex-based). Заполняется только при построении без `--no-calls`.

| Колонка       | Тип                  | Описание                             | Пример                                                           |
| ------------- | -------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| `id`          | INTEGER PK           | Идентификатор                        | `2376925`                                                        |
| `caller_id`   | INTEGER FK → methods | Кто вызывает (ссылка на methods)     | `388066`                                                         |
| `callee_name` | TEXT                 | Кого вызывает (имя или Модуль.Метод) | `НоменклатураСервер.УстановитьУсловноеОформлениеЕдиницИзмерения` |
| `line`        | INTEGER              | Номер строки вызова в исходном файле | `1135`                                                           |
| `callee_key`  | TEXT (nullable, v14+) | Стабильный ключ цели `<rel_path>::<casefold(метод)>` или NULL | `CommonModules/НоменклатураСервер/Ext/Module.bsl::установитьусловноеоформлениеединицизмерения` |

Направление чтения: **caller → callee** (кто → кого). `callee_name` хранится as-is (имя или `Модуль.Метод`).

**Извлечение вызовов (v1.16.0):** обход тела метода идёт через многострочный сканер `_scan_module` (а не построчный `_strip_code_line`), поэтому функции языка запросов внутри многострочных строковых литералов (`ЕСТЬNULL(`, `ВЫРАЗИТЬ(`, `СУММА(` в текстах запросов с `|`-продолжением) больше **не** попадают в граф как ложные рёбра.

**Привязка к методу (`callee_key`, v14+).** Чтобы реверс-граф не склеивал одноимённые методы (`ПриЗаписи`/`ОбработкаПроведения` из сотен модулей), каждое ребро при построении пытается разрешиться в **стабильный текстовый ключ цели** `<target_rel_path>::<casefold(method_name)>`. Ключ основан на `rel_path` (UNIQUE, переживает инкремент и пересоздание rowid) — в отличие от `methods.id`, который переназначается при перестройке изменённого модуля. Резолвятся только два доказуемо-безопасных tier'а:

- **local** — голый вызов `B()` → метод того же модуля вызывающего;
- **common_exported** — квалифицированный `A.B()` → экспортный метод общего модуля `A` (`category=CommonModules`, `module_type=Module`, `is_export=1`).

Object/manager-вызовы (`Справочники.X.Метод`, `Контрагент.Метод`) и платформенные/внешние методы **намеренно не резолвятся** → `callee_key IS NULL` (это методы переменной/менеджера/платформы, автоматический резолв дал бы ложные привязки). Неоднозначность (несколько кандидатов на tier'е) → тоже NULL. Нерезолвленные рёбра честно остаются на матче по имени (recall не теряется). Агрегаты резолва пишутся в `index_meta`: `calls_total` / `calls_resolved`.

**Консистентность `callee_key` при инкременте (v1.21.0).** Инкремент пересобирает рёбра помодульно и резолвит только рёбра переобработанного батча, поэтому при изменении **общего модуля** `A` (rename/delete/export-flip/add экспортного метода) `callee_key` рёбер `A.B` из **нетронутых** вызывателей раньше «замерзал» (recall сохранялся через name-fallback, но `calls_resolved` и exact/fallback-метрики расходились со свежим `build`). Теперь оба пути `update` собирают casefold-имена общих модулей дельты (новые — из распарсенных модулей, старые — из БД до удаления) и точечно **пере-резолвят** только qualified-рёбра `A.B` к этим именам тем же резолвером, что и `build` → строгий инвариант `update ≡ build` по `callee_key`. Уже накопленный на существующих v14-индексах дрейф лечится **одноразовым глобальным пере-резолвом** на следующем `update` (идемпотентно по флагу `index_meta.qualified_callers_reresolved`, как разовая чистка шума в v1.17.0) — **без смены `BUILDER_VERSION` и без пересборки**. Резолв `local`-tier'а дрейфовать не может (цель в том же файле → переобрабатывается вместе). Обратный код-индекс `metadata_code_usages` дрейфу этого рода **не подвержен** — он хранит сырой текст ссылки, а не резолвенный указатель.

**Производительность лукапов резолвера при инкременте (v1.21.0).** Раньше `_bulk_insert` строил лукапы резолва полным сканом всех методов БД на **каждом** инкременте (≈1.6–2.2 с на конфигурациях 500–630K методов — платилось даже на правке одного файла). Теперь батч-локальные `methods_by_module` и `local_lookup` (нужны только для модулей текущего батча; голый `B()` указывает в свой же модуль) строятся узким `WHERE module_id IN (…)` по `idx_meth_module`, когда батч мал (порог < `SQLITE_MAX_VARIABLE_NUMBER`); полный `build`/крупный батч — прежний полный скан. БД-широкий tier `common_exported` (цель может быть в неизменённом общем модуле) берётся отфильтрованным SQL (только экспортные методы общих модулей), а не Python-сканом всех методов. На 1-файловом git-инкременте крупной базы лукапы ускорились ~**300×** (1.6 с → ~5 мс). Корректность не меняется (тот же резолвер, `ORDER BY module_id, line` сохранён — `method_idx` рёбер индексирует список методов по строке); `BUILDER_VERSION` не тронут.

**Точный режим в `get_callers` / `find_call_hierarchy`.** Если цель запроса разрешается в ровно один модуль, callers ищутся по `callee_key` (коллизии одноимённых методов из других модулей отсекаются), а нерезолвленные (`callee_key IS NULL`) name-рёбра остаются как fallback для recall. В `_meta` возвращаются `exact_rows` / `fallback_rows` / `exact_available`, чтобы потребитель различал точные и эвристические рёбра. `find_call_hierarchy(name, …, module_hint=…)` дизамбигуирует корень (для одноимённых объектных методов), а на глубине распространяет `rel_path` найденного caller'а как hint → точность сохраняется автоматически. На v13-индексе (колонки ещё нет, читается до фоновой пересборки) точный режим выключен: `exact_available=False`, чистый name-based-поиск.

**Производительность матча по имени (v1.16.0).** Матч вызывающих по имени идёт через равенство по индексируемому выражению, а не через `LIKE '%.имя'` (ведущий `%` запрещал использование индекса → полный скан `calls`). Так как `callee_name` всегда имеет ≤1 точку, суффикс после точки = имя метода → индекс `idx_calls_callee_short` (`CASE WHEN instr(callee_name,'.')>0 THEN substr(...) ELSE callee_name END` с `COLLATE NOCASE`) обслуживает голое имя; ввод с точкой (`Модуль.Метод`) бьёт по полному `idx_calls_callee`. Индекс — чистая оптимизация (запрос корректен и без него), `BUILDER_VERSION` не менялся; на уже собранных v14-базах создаётся через self-heal при любом `update()`. У `find_call_hierarchy` есть backstop `_HIERARCHY_VISITED_CAP=2000` от взрыва обхода на широком корне без hint (например `ОбработкаПроведения`): BFS по уровням останавливается, возвращает частичное связное дерево и помечает `_meta.node_budget_exceeded=True` + `visited_cap`.

Ещё две per-node издержки exact-режима устранены тем же релизом: (1) резолв цели `_resolve_target_key` (по `module_hint`) бил по `methods JOIN modules` с `py_lower(name)` без индекса на FK-колонке → полный `SCAN methods`; индекс `idx_meth_module ON methods(module_id)` (в `_SCHEMA_SQL` + self-heal на `update()`) переводит его в точечный `SEARCH (module_id=?)`. (2) Проверка «таблица `calls` не пуста» в `get_callers`/`has_calls` сделана через `SELECT 1 FROM calls LIMIT 1` вместо `COUNT(*)` (полный счёт всех рёбер). Обе — чистые оптимизации без смены `BUILDER_VERSION`.

### methods_fts (FTS5)

Виртуальная таблица полнотекстового поиска методов. Строится по умолчанию, отключается флагом `--no-fts`. Использует trigram-токенайзер — разбивает имена на тройки символов для подстрокового поиска с BM25-ранжированием.

```sql
CREATE VIRTUAL TABLE methods_fts USING fts5(name, object_name, tokenize='trigram');
```

Данные копируются из `methods` + `modules` (имя метода + имя объекта-владельца). Поиск:

```sql
SELECT m.name, mod.object_name, methods_fts.rank
FROM methods_fts
JOIN methods m ON m.id = methods_fts.rowid
JOIN modules mod ON mod.id = m.module_id
WHERE methods_fts MATCH '"Документ"'
ORDER BY methods_fts.rank
LIMIT 30;
```

**Пример результата** (поиск "Документ"):

| name                          | object_name       | rank  |
| ----------------------------- | ----------------- | ----- |
| ОбработкаПроведенияДокументов | ДокументыМенеджер | -3.82 |
| ПолучитьСписокДокументов      | ОбщегоНазначения  | -2.41 |

Значение `rank` — BM25 score (отрицательное, ближе к 0 = менее релевантно).

**Размер:** +232 MB на ERP (~569K методов с длинными русскими CamelCase-именами). **Время построения:** +5 секунд к общему build. Отключение: `--no-fts`.

**Обратная совместимость:** на v8 индексе все методы возвращают `None` / `{}` через `try/except OperationalError`. `update()` создаёт таблицу через `CREATE TABLE IF NOT EXISTS`.

> **v1.30.0 — read-time форма строк, persisted-данные не менялись.** `get_overrides` и `find_ext_overrides` отдают ЕДИНЫЙ набор ключей: индексные строки дополняются алиасами `module_path`/`line`/`module_type`, live-строки — `ext_module_path`/`ext_line`/`source_*`. Дополнение аддитивное, на копиях, значения существующих полей не меняются, порядок и состав среза 200 сохранены (ключ сортировки считается ДО обогащения). Пустой `extension_method` в таблице по-прежнему возможен: сканер аннотаций смотрит фиксированное окно после аннотации, и объявление, отделённое длинным блоком комментариев, в него не попадает. Read-time лечение таких строк — известное ограничение, оно требует отдельной работы и здесь НЕ выполняется.

### metadata_code_usages (Level-13, v13+)

Обратный индекс использований объектов метаданных **В КОДЕ** — основа для `find_code_usages()` и режима `find_references_to_object(..., include_code=True)`. В отличие от `metadata_references` (декларативные ссылки из метаданных-XML), эта таблица — **код-производная**: наполняется из тел `.bsl`-модулей в том же проходе, что `regions`/`module_headers` (нулевой доп. I/O), и привязана к `module_id`. Одна строка = одно обращение.

| Колонка          | Тип        | Описание                                                                 | Пример                              |
| ---------------- | ---------- | ------------------------------------------------------------------------ | ----------------------------------- |
| `id`             | INTEGER PK | Идентификатор                                                            | `1`                                 |
| `module_id`      | INTEGER FK | Модуль-источник обращения (→ `modules.id`)                               | `4711`                              |
| `object_ref`     | TEXT       | Канонический ref на объект (display-форма)                               | `Document.ПриобретениеТоваровУслуг` |
| `object_ref_key` | TEXT       | `object_ref.lower()` — для indexed Cyrillic-aware exact-lookup без UDF   | `document.приобретениетоваровуслуг` |
| `member_path`    | TEXT       | Имя ТЧ для `query` (3-я группа пути), иначе `NULL`                       | `Товары` или `null`                 |
| `usage_kind`     | TEXT       | Вид обращения: `manager` \| `ref_type` \| `query`                       | `manager`                           |
| `line`           | INTEGER    | Номер строки в модуле                                                    | `42`                                |

Индекс: `idx_mcu_ref` (по `object_ref_key` — единственный, ради веса; индекса по `module_id` нет — инкрементальное удаление идёт чанкованным `DELETE ... WHERE module_id IN (chunk)`).

**Что ловит** (лёгкий источник-aware regex-слой):
- `manager` — обращение к менеджеру коллекции `Документы.X` / `Documents.X` (ищется в коде; строки и комментарии сняты через multiline-aware `_scan_module`);
- `ref_type` — тип в строковом литерале `"ДокументСсылка.X"` (RU) / `"DocumentRef.X"` (EN, через `canonicalize_type_ref` в строгом BUILD-режиме). Публичная нормализация принимает регистр-независимые варианты, но BUILD сохраняет прежнее регистрозависимое множество входов до отдельной миграции builder version;
- `query` — путь метаданных в тексте запроса (строковый литерал) `Документ.X` и `Документ.X.Товары` (3-я группа = имя ТЧ → `member_path`).

**Что НЕ ловит** (осознанно, документировано):
- доступ к реквизитам/ТЧ через локальные переменные (`Док = Документы.X; Док.Товары.Количество`) — требует инференса типов, вне охвата;
- категории вне явной таблицы форм v1: `DocumentJournals` (`ЖурналДокументов.`), `FilterCriteria` (`КритерийОтбора.`) — редки как typed reverse-usage, легко добавить строкой в `_RU_META_FORMS`;
- **код расширений** — в индекс входят только модули основной конфигурации (как у `find_references_to_object`).

**Источник форм** — `bsl_xml_parsers._RU_META_FORMS` (единый словарь RU/EN singular/plural/reftypes), из него строятся `_CODE_MANAGER_COLLECTIONS` / `_CODE_QUERY_COLLECTIONS` / `_RU_REFTYPE_TO_CANONICAL`. Русские формы нерегулярны (`РегистрСведений`→`РегистрыСведений`) и заданы явно.

**Инкремент:** при изменении `.bsl`-модуля строки пересобираются по обоим путям update (git-fast-path и full-scan) — чанкованный `DELETE` по `module_id` затронутых модулей до удаления `modules` и до `_bulk_insert` (FK-safe), затем переINSERT через общий `_bulk_insert`. Таблица код-производная → при апгрейде индекса старее v13 выполняется **разовый полный rebuild** (как при добавлении `regions` в v8).

**IndexReader API:**
- `find_code_usages(object_ref, kind=None, limit=1000)` — JOIN к `modules`, возвращает `{path, object_name, category, module_type, line, kind, member}`; `None` только если таблицы нет (старый индекс).
- `count_code_usages(object_ref, kind=None)` — `{total, by_kind}` без выборки строк.

Ускоряет хелперы: `find_code_usages()`, `find_references_to_object(..., include_code=True)`.

## 6. Инкрементальное обновление

Команда `index update` работает по следующему алгоритму:

1. Сканирует текущие `.bsl`-файлы на диске
2. Сравнивает `mtime` и `size` каждого файла с сохранёнными значениями в таблице `modules`
3. Определяет дельту: добавленные (новые файлы), изменённые (расхождение mtime/size), удалённые (файл исчез с диска)
4. Обновляет только затронутые файлы в одной транзакции: удаляет старые записи из `modules`, `methods`, `calls`, затем вставляет новые
5. Неизменённые файлы (как правило, 99%+ кодовой базы) не читаются с диска вообще
6. Выполняет schema upgrade (`CREATE TABLE IF NOT EXISTS`) для таблиц, добавленных в новых версиях — обеспечивает совместимость индексов, собранных старыми версиями
7. Полностью пересчитывает метаданные (Level-2, Level-5), роли, `file_paths` и `detected_prefixes`

На практике инкрементальное обновление ERP (~24K файлов) после изменения нескольких модулей
занимает ~5 минут (полный скан). При наличии git — **5-20 секунд** для BSL-only изменений.

### Консистентность при изменениях во время build/update

Снимок файловой системы **не** выполняется ни при `build`, ни при `update` —
файлы читаются as-is на момент обращения. Если исходники меняются параллельно
(другой разработчик, выгрузка из конфигуратора, `git pull`), возможны гонки:

| Сценарий | Что произойдёт | Как исправляется |
|----------|----------------|------------------|
| Файл изменился между сканом и чтением | В индекс попадёт новая версия | — (данные свежее ожидаемых, не stale) |
| Файл удалён между сканом и чтением | `_process_single_file` вернёт `None`, файл пропущен | Следующий `update` его удалит |
| Файл изменён и **закоммичен** до конца операции | Не попадёт в dirty-снимок | **Git path:** `git diff` найдёт при следующем `update`. **Full scan:** `mtime`/`size` изменились — обнаружит при следующем `update` |
| Файл изменён и **остался dirty** к моменту завершения | **Git path:** попадёт в dirty-снимок (`git_dirty_paths`) → принудительно войдёт в дельту при следующем `update`. **Full scan:** `mtime`/`size` изменились → обнаружит | — |
| Файл в процессе записи (partial write) | Теоретически — неполные данные в индексе | Маловероятно: BSL-файлы малы, запись near-atomic на уровне ОС |

**Рекомендация:** после массовых изменений (merge, rebase, выгрузка из конфигуратора)
выполните `index update` **после** завершения всех файловых операций.
Один дополнительный `update` гарантирует полную консистентность.

### 6.1. Git-ускоренное инкрементальное обновление

Если каталог исходников находится внутри git-репозитория,
команда `index update` автоматически использует git для определения изменённых файлов
вместо полного обхода файловой системы. Каталог `.git` может быть как в самом
каталоге исходников, так и выше по дереву каталогов (типичная ситуация для EDT-проектов,
где `.git` в корне репозитория, а исходники в `src/`).

#### Как это работает

1. При `build` или `update` в `index_meta` сохраняется SHA коммита HEAD
   (`git_head_commit`).
2. При следующем `update`:
   - Проверяется наличие git-репозитория (`git rev-parse --is-inside-work-tree`)
     и команды `git` в PATH.
   - Определяется корень git-репозитория и вычисляется префикс пути
     (`base_path` относительно `git_root`).
   - Запрашивается дельта у git: все файлы, изменённые после сохранённого коммита
     (committed + staged + unstaged + untracked). Из путей вычитается префикс,
     чтобы получить пути, совместимые с индексом.
   - Из дельты выделяются `.bsl`-файлы → обновляются `modules`, `methods`, `calls`,
     `methods_fts`, `regions`, `module_headers`, `register_movements`, `metadata_code_usages`.
   - Если среди изменённых файлов есть `.xml`, `.mdo`, `.rights`, `.form`,
     `.xdto` — **селективно** пересобираются таблицы метаданных только для
     затронутых категорий (Level-2/5/6/8/9).
   - Если метаданные не менялись (только `.bsl`) — таблицы метаданных
     не пересобираются, `file_paths` обновляется инкрементально.
   - `extension_overrides` пересобираются при любой BSL-дельте.
   - Level-1 metadata (`config_name`, `config_version`, `shallow_bsl_count` и др.)
     обновляется всегда, независимо от типа изменений.
3. Обновлённый `git_head_commit` сохраняется в `index_meta`.

#### Git-команды, используемые для дельты

| Команда | Что находит |
|---------|-------------|
| `git diff --name-only --no-renames <saved_sha> HEAD` | Файлы, изменённые в новых коммитах (критичная команда — сравнение git-объектов, без чтения рабочего дерева) |
| `git diff --numstat --ignore-cr-at-eol --no-renames --cached` | Файлы в staging area |
| `git diff --numstat --ignore-cr-at-eol --no-renames` | Файлы, изменённые в рабочей копии |
| `git ls-files --others --exclude-standard` | Новые (untracked) файлы |

> **Почему `--numstat --ignore-cr-at-eol`, а не `--name-only`** (для рабоче-древесных diff):
> только эта комбинация **исключает** файлы, отличающиеся исключительно концами строк
> (CRLF↔LF), — `--name-only` даже с флагом `--ignore-cr-at-eol` продолжает их перечислять.
> Это важно для Windows-выгрузок в Linux-окружении (blob в git — LF, рабочее дерево — CRLF):
> без этого инкремент ложно посчитал бы изменённым весь репозиторий. Committed-diff остаётся
> на `--name-only` — он сравнивает git-объекты, рабочего дерева не касается, CRLF ему не мешает.

#### Матрица инвалидирования таблиц

Обновление метаданных выполняется **селективно по категориям**: если изменился
файл в `Catalogs/`, пересобираются только таблицы, относящиеся к справочникам.

Замер на боевом CF-проекте: 10 109 файлов форм, 258 100 строк, **45 с** на один инкрементальный `update`, затронувший хотя бы одну форму. Так было и для `.form`; с v1.33.0 то же распространено на CF, иначе правка CF-формы не отражалась в индексе вообще. Селективность — отдельная задача, в v1.33.0 не вводится |

#### Fallback на полный скан

Git-ускорение автоматически отключается (с прозрачным fallback на полный скан), если:

- Каталог исходников не находится внутри git-репозитория
- Команда `git` не найдена в PATH
- В `index_meta` нет сохранённого `git_head_commit` (первый update
  после build старой версией — `git_head_commit` записывается для следующего раза)
- Сохранённый коммит не найден в истории (force push, rebase, shallow clone)
- Версия индекса (`builder_version`) отличается от текущей.
  С v15 расхождение **ниже порога** означает не просто отключение git-ускорения, а
  **принудительную полную пересборку** индекса на месте: полный СКАН считает дельту
  по mtime/size и нетронутые модули не перечитывает, поэтому старое содержимое
  пережило бы бамп. Порог живёт отдельной константой в `IndexBuilder._update_locked()`
  (`if old_version < 15`) и поднимается вместе с `BUILDER_VERSION`, когда меняется
  не только схема, но и СОДЕРЖИМОЕ производных таблиц
- Критичная git-команда (`merge-base`, `git diff <saved>..HEAD`) завершилась ошибкой или таймаутом (60 сек)
- **Предыдущий детект незакоммиченного был помечен как ненадёжный** (`git_dirty_unreliable=1` — см. ниже)

#### Надёжность детекта незакоммиченного (`git_dirty_unreliable`, v1.13.0+)

Рабоче-древесные команды (staged/unstaged/untracked) — **best-effort**: они выполняют
`stat()`/чтение каждого файла рабочей копии и на медленной ФС (Docker Desktop / Virtiofs)
могут превысить таймаут `RLM_GIT_DIRTY_TIMEOUT` (по умолчанию **120 сек**).

Чтобы при этом **не потерять незакоммиченные правки молча** (поведение до v1.13.0 — баг H-A:
при таймауте команды возвращали пустой результат, и незакоммиченная правка не попадала в индекс),
при таймауте/ошибке любой из этих команд детект помечается как **ненадёжный**:

1. Текущий `update` **уходит в полный скан** (mtime/size-дельта — она в этом случае надёжнее
   частичного git-результата), а не доверяет неполному набору git.
2. В `index_meta` записывается флаг `git_dirty_unreliable=1`. Прежний хороший `git_dirty_paths`
   при этом **не затирается** частичным набором.
3. На **следующем** `update` флаг читается из `index_meta` (мгновенно, без запуска git — поэтому
   fallback по причине `prev dirty unreliable` срабатывает без всякого ожидания таймаута) и снова
   форсит полный скан — пока не удастся снять **надёжный** dirty-снимок, после чего флаг
   сбрасывается в `0` и git fast path снова доступен.

Причина ухода в полный скан печатается в `git_fallback_reason` (в результате `index update`
и в CLI), а в логе — строкой `Git fast path unavailable (<reason>), using full scan`.

> **CRLF-залипание.** Если рабочее дерево CRLF, а индекс/blob — LF (типичная Windows-выгрузка
> под Docker на Windows), `git diff` вынужден перечитывать **всё** дерево через Virtiofs и
> стабильно не укладывается в таймаут. Тогда `git_dirty_unreliable` остаётся `1`, и **каждый**
> `update` идёт полным сканом (корректно, но медленно). Лечится нормализацией концов строк
> (`.gitattributes` с `* text=auto eol=lf`) — рабочее дерево совпадёт с blob, детект станет
> мгновенным и флаг снимется. Как временную меру можно поднять `RLM_GIT_DIRTY_TIMEOUT`.

#### Dirty-снимок

При каждом update сохраняется список файлов, находившихся в dirty-состоянии
(staged, unstaged, untracked) на момент индексации. При следующем update
эти файлы принудительно включаются в дельту — даже если git их больше не показывает.
Это гарантирует, что переход `dirty → clean` не оставит stale-данные в индексе.

#### Производительность

**Нативная FS (Windows / Linux):**

| Конфигурация | Полный скан (fallback) | Git fast path, BSL-only | Git fast path, BSL + XML |
|-------------|------------------------|--------------------------|--------------------------|
| ЕРП (~24K bsl) | ~5 мин | < 20 сек* | зависит от числа категорий |
| БГУ (~14K bsl) | ~3 мин | **17 сек** | — |
| CRM (~3K bsl) | ~30 сек | — | **5 сек** |

\* Оценка; замер на БГУ: 16.9 сек при 14.5K модулей.

**Docker Desktop / Virtiofs (Windows + WSL2):**

Virtiofs добавляет значительный I/O overhead на `stat()` вызовы.

| Конфигурация | Full build | Git fast path, BSL-only | Git fast path, все категории |
|-------------|------------|--------------------------|-------------------------------|
| ДО3 (~6K bsl) | 22 мин | **5 мин** (4.5× ускорение) | 16 мин (1.4× ускорение) |

Основное время в Docker тратится на `extension_overrides` rebuild и selective
metadata refresh — оба выполняют XML-парсинг через Virtiofs.
При BSL-only изменениях metadata не пересобирается, ускорение максимальное.

#### Разделение trigger-наборов

Git fast path использует **раздельные trigger-наборы** по расширению файла,
а не единый набор для всех метаданных:

| Расширение | Что триггерит | Что НЕ триггерит |
|------------|---------------|-------------------|
| `.xml`, `.mdo` | Категорийные таблицы (`object_attributes`, `object_synonyms`, `event_subscriptions` и др.) по `changed_categories` + synonym-rescan | `form_elements`, `role_rights` |
| `.form` | Только `form_elements` | Категорийные таблицы |
| `.rights` | Только `role_rights` | Категорийные таблицы |
| `.xdto` | Только `xdto_packages` (через category) + synonym-rescan | `form_elements`, `role_rights` |
| `.command` (v1.9.3+) | `metadata_references` (per-object commands и `CommonCommands`) — pointwise или fallback | **Synonym-rescan не запускается** на чистой `.command`-дельте |

`changed_categories` (для metadata refresh) строится из `.xml`/`.mdo`/`.xdto`/`.command` —
это первый сегмент пути (например `Catalogs/Номенклатура/Номенклатура.xml` → `Catalogs`).
Изменение `.form` в `Documents/` **не** приведёт к пересборке `object_attributes` Documents.

`synonym_changed_categories` (для category-wide synonym rescan) строится **только** из
`.xml`/`.mdo`/`.xdto` — без `.command`. Это защищает от perf-регрессии: чистая
`.command`-дельта (например, изменение `CommonCommands/X/X.command`) обновляет
`metadata_references` через bulk fallback, но **не** триггерит DELETE+rescan
`object_synonyms` для целой категории.

**Configuration.xml** (корень конфигурации) не попадает ни в одну категорию,
но Level-1 metadata (`config_name`, `config_version` и др.) обновляется **безусловно**
при каждом update — вне зависимости от типа изменений.

#### Pointwise incremental refresh (v1.9.3+)

Для **узкого whitelist категорий** git fast path обновляет индекс **точечно**
(per-object DELETE+INSERT) вместо category-wide rescan. На больших конфигурациях
(Тест ERP, 1000+ объектов в `Catalogs`) это основной источник времени
инкрементального обновления: изменение одного атрибута больше не порождает
парсинг всех 1000 справочников.

**Whitelist (Group A — категорийные таблицы):**
`Catalogs`, `Documents`, `InformationRegisters`, `AccumulationRegisters`,
`AccountingRegisters`, `ChartsOfAccounts`.

**Whitelist (Group B — глобальные таблицы):**
`EventSubscriptions`, `ScheduledJobs`, `XDTOPackages`.

Любая категория **вне whitelist** (`Reports`, `Constants`, `FunctionalOptions`,
`Subsystems`, `Roles`, `ChartsOfCharacteristicTypes`, `DefinedTypes`,
`ExchangePlans`, `CommonCommands`, `DocumentJournals`, `Tasks`, `BusinessProcesses`,
`ChartsOfCalculationTypes`, `DataProcessors`) **всегда** идёт через bulk fallback —
поведение строго эквивалентно полному category-wide rescan.

**Покрываемые таблицы:** `object_attributes`, `predefined_items`, `object_synonyms`,
`metadata_references`, `event_subscriptions`, `scheduled_jobs`, `xdto_packages`.

**Soft fallback thresholds.** Точечный путь автоматически уступает bulk-collect, если:

| Условие | Порог |
|---------|-------|
| Категория не в whitelist | мгновенно |
| Не удалось разрешить корневой/нестандартный путь в `(category, object_name)` | мгновенно |
| Любое исключение в `_refresh_object*` (через SAVEPOINT-rollback) | мгновенно, категория уходит в fallback |
| `len(changed_objects) >= 50` | абсолютный (`_POINTWISE_MAX_OBJECTS`) |
| `len(changed_objects) >= 0.5 × total_in_category` | относительный (`_POINTWISE_MAX_RATIO`) |

**Идемпотентность legacy-индексов.** На индексах, собранных pre-v1.9.0 (без таблиц
`metadata_references` / `object_synonyms`), pointwise молча пропускает DELETE/INSERT
в отсутствующие таблицы — поведение **строго эквивалентно** bulk path. Чтобы получить
полную выгоду точечного пути и таблицу `metadata_references`, выполните однократный
`rlm_index(action="build", ...)`.

**Telemetry.** После каждого incremental update в логе одна INFO-строка:

```
git fast path: pointwise refresh used for N categories (M objects),
fallback used for K categories (reasons: {'not_eligible': 2, 'threshold_absolute': 1, ...}),
bsl modules incremental: L
```

Возможные значения `reasons`: `not_eligible`, `unresolved_root`, `no_objects`,
`threshold_absolute`, `threshold_relative`, `refresh_exception`.

#### Добавление новых категорий / таблиц (чеклист для разработчика)

При добавлении новой metadata-таблицы, привязанной к категории 1С, необходимо
обновить git fast path в четырёх точках `bsl_index.py`:

1. **`_collect_metadata_tables()`** — добавить `collect_xxx: bool = True` kwarg
   и обернуть соответствующий блок сбора в `if collect_xxx`
2. **`_update_git_fast()`** — добавить trigger-флаг:
   `collect_xxx="NewCategory" in changed_categories`
3. **`_insert_metadata_tables_selective()`** — добавить маппинг
   `"new_table": "NewCategory"` в `_TABLE_CATEGORY_MAP` и SQL в `_TABLE_INSERT_SQL`
4. Если таблица имеет поле `category` — добавить селективный
   `DELETE FROM new_table WHERE category = ?` (по аналогии с `object_attributes`)

Без этих изменений новая таблица будет корректно пересобираться при **fallback**
(полный скан), но **не** при git fast path — данные станут stale после
инкрементального обновления.

#### Известные ограничения

- Файлы, перечисленные в `.gitignore`, но физически присутствующие в каталоге
  исходников, не попадут в дельту при git fast path. При полном скане (fallback)
  такие файлы обрабатываются. На практике `.bsl`-файлы не добавляют в `.gitignore`.

## 7. Проверка свежести (Staleness Detection)

Проверка свежести выполняется на двух уровнях:

### Quick check (rlm_start)

При старте сессии (`rlm_start`) используется облегчённая проверка `check_index_usable`, которая **не выполняет rglob по файловой системе** — это критично для больших конфигураций и сетевых дисков:

1. **Проверка возраста** (`RLM_INDEX_MAX_AGE_DAYS`) — если индекс старше порога, статус `STALE_AGE`
2. **Пропуск для молодых индексов** (`RLM_INDEX_SKIP_SAMPLE_HOURS`) — если индекс моложе порога, сразу `FRESH`
3. **Выборочная проверка содержимого** — из индекса случайно выбирается `RLM_INDEX_SAMPLE_SIZE` файлов (по умолчанию 5), stat()-вызовы выполняются параллельно. Если более 20% выборки не совпадает, статус `STALE_CONTENT`

Дополнительно (только при disk path): `rlm_start` сравнивает `bsl_file_count` из `detect_format()` с `shallow_bsl_count` из `index_meta` (одинаковая методика подсчёта, depth≤4). Расхождение >5% добавляет предупреждение. При fast-path startup (fresh index) drift check пропускается — обе метрики из одного источника.

В ответе `rlm_start` поле `"index_check": "quick"` — явный сигнал, что полная структурная проверка не выполнялась.

### Strict check (CLI `index info`)

Команда `rlm-bsl-index index info` выполняет полную проверку `check_index_strict`:

1. **Структурная проверка** (`bsl_count` + `paths_hash`) — если количество файлов изменилось или набор путей не совпадает (файлы добавлены/удалены), статус `STALE`
2. **Проверка возраста** (`RLM_INDEX_MAX_AGE_DAYS`) — если индекс старше порога, статус `STALE_AGE`
3. **Выборочная проверка содержимого** — аналогично quick check

### Рекомендуемая стратегия обновления

Для проектов средней загруженности (несколько разработчиков, ежедневные изменения):

- **После получения обновлений (git pull):** `rlm-bsl-index index update <path>` (полный скан ~5 мин для ERP; при наличии git и BSL-only изменениях — **5-20 сек**)
- **При наличии git:** `index update` автоматически использует git для
  определения изменений — полный обход FS не выполняется. Время обновления
  не зависит от размера конфигурации, только от объёма изменений.
- **Раз в неделю или после крупных изменений:** `rlm-bsl-index index build <path>` (полная перестройка)
- **Полная проверка состояния:** `rlm-bsl-index index info <path>`

### MCP SDK: рекомендуемый client timeout

При запуске `rlm_start` на очень больших конфигурациях (>20K BSL-файлов) время инициализации может превышать 30 секунд, особенно на медленных дисках или сетевых ресурсах. Если MCP-клиент устанавливает timeout ниже этого значения, может произойти ошибка `AssertionError: Request already responded to` в MCP SDK — клиент отправляет timeout-ответ, а сервер пытается ответить после завершения обработки.

**Рекомендация:** установить client timeout не менее 60 секунд. С оптимизациями v1.3.1 (fast-path startup из index_meta) время `rlm_start` сокращается до <1 секунды при наличии fresh-индекса, 10-15 секунд без индекса.

Если проверка выявила устаревание, агент получает предупреждение с рекомендацией запустить `index update` или `index build`.

## 8. Интеграция в хелперы (прозрачное ускорение)

### search_methods — полнотекстовый поиск

```python
search_methods(query, limit=30) -> list[dict]
```

Полнотекстовый поиск методов по подстроке имени через FTS5-индекс. Возвращает результаты, отсортированные по BM25-релевантности. Без индекса или без FTS — возвращает пустой список.

Пример:

```python
results = search_methods("ОбработкаЗаполнения")
for r in results:
    print(f"{r['name']} ({r['type']}) в {r['module_path']}")
```

## 9. Граф вызовов — ограничения

Граф вызовов строится **эвристически** (regex-разбором), а не на основе AST:

- **Ложные срабатывания:** В граф могут попасть конструкторы (`Новый ТипОбъекта()`) и функции платформы. С v1.16.0 совпадения внутри **многострочных** строковых литералов (тексты запросов с `|`-продолжением: `ЕСТЬNULL(`, `ВЫРАЗИТЬ(`, `СУММА(`) больше не попадают в граф — извлечение идёт многострочным сканером `_scan_module`
- **Привязка к методу (`callee_key`, v14+):** ребро дополнительно резолвится в стабильный ключ `<rel_path>::<метод>` для двух безопасных tier'ов (local + common-exported). Это даёт точный режим в `get_callers`/`find_call_hierarchy` (одноимённые методы из разных модулей не склеиваются). Object/manager-вызовы (`Справочники.X.Метод`, `Контрагент.Метод`) и платформенные методы **намеренно не резолвятся** (`callee_key IS NULL`) — `callee_name` для них хранится как есть; такие рёбра обслуживаются матчем по имени (fallback). Доля resolved видна в `index_meta.calls_resolved` / `calls_total`
- **Отсутствие различения:** Парсер не отличает вызов метода (`Метод()`) от обращения к переменной, оборачивающей вызов
- **Маркировка доверия:** в `_meta` точных хелперов возвращаются `exact_rows` / `fallback_rows` / `exact_available` — точные (resolved) рёбра отделены от эвристических (по имени)
- **Рекомендация:** Для критического анализа (рефакторинг, удаление метода) результаты из графа вызовов следует верифицировать через live-хелперы `read_procedure` и `find_callers_context`, которые работают по актуальным файлам

## 10. Known issues и ограничения

- **UNIQUE(module_id, name, line)** — парсер может создать дубликаты для нестандартного кода (например, несколько процедур с одинаковым именем в одном модуле). При конфликте используется `INSERT OR REPLACE`
- **Переименование методов общих модулей** — с v1.21.0 инкрементальное обновление пере-резолвит `callee_key` входящих рёбер `A.B` из нетронутых вызывателей при изменении общего модуля `A` (rename/delete/export-flip/add), поэтому граф остаётся консистентным со свежим `build` без `index build` (см. «Консистентность `callee_key` при инкременте»). Накопленный на старых v14-индексах дрейф снимается одноразово на следующем `update`. Переименование метода объектного/менеджерного модуля по-прежнему опирается на матч по имени (эти tier'ы намеренно не резолвятся в `callee_key`)
- **Точность mtime** — зависит от файловой системы (FAT32 — 2 сек, NTFS — 100 нс, ext4 — 1 нс). Допуск в 1 секунду учтён при сравнении
- **Время первого построения** — на ERP полный `index build` (calls + metadata + FTS + synonyms + form_elements + attributes + predefined): CF (~23K модулей, ЕРП 2.5.14) — **~512с**, EDT (~20K модулей, ЕРП 2.5.7) — **~448с**, CF (БГУ 2.0.105, ~14K модулей) — **~324с**. FTS добавляет ~5 секунд, synonyms добавляет ~3-5 секунд. Без графа вызовов (`--no-calls`) — ~30-90 секунд
- **Потребление памяти при построении** — все результаты парсинга (методы + вызовы) накапливаются в ОЗУ до момента записи в SQLite. На конфигурации ERP пиковое потребление составляет ~3 GB RAM. Если на машине мало оперативной памяти, используйте `--no-calls` для снижения нагрузки
- **`extension_purpose`** — ключ в `index_meta` присутствует только для расширений (`config_role = extension`). Для основных конфигураций не записывается
- **Размер БД** — CF (ЕРП 2.5.14, 23K модулей): **~1323 MB** (calls + metadata + FTS + synonyms + form_elements + attributes + predefined). EDT (ЕРП 2.5.7, 20K модулей): **~1112 MB**. CF (БГУ 2.0.105, 14K модулей): **~854 MB**. Без FTS (`--no-fts`) — на ~230 MB меньше. Без графа вызовов (`--no-calls`) — ~35 MB
